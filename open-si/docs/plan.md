# /plan procedure

/plan is where captures become batches through discussion. No building happens here.

Claude owns dependency management — ordering, grouping, dependencies — through discussion, not silently.

## Ground rules

- Never build during /plan. Want to write code? Queue it.
- Batches are build, test, or audit work, in any combination. Nothing else.
- Never queue thinking work as a batch. Reviews, reconciliations/drift checks, and design exploration are planning work — their output is decisions, not changed files. Run them inside /plan; they spawn batches as output. Audit work is a separate category, not an exception: an audit is defined by its output contract — findings routed through Captures, no direct edits to the artifacts it reads. Audits produce findings, thinking work produces decisions; the two don't overlap. Test: output is decisions → planning work, run it in /plan; output is findings from a systematic read, routed to Captures → audit batch. The same test applies per seeded item, not just per batch: an audit's seeded check-items must be finding-shaped; decision-shaped checks (reconciliation, is-this-already-resolved) get resolved at planning time, not queued. And the output contract is mechanical: an audit names no write-target doc in its Files and sets no file-writing Output — a document as the deliverable is a build authored later from vetted findings, never written at the audit stage (see Step 3's audit-batch guard).
- Audit batch vs inline read — the size axis. The findings-vs-decisions test above sorts by output shape; it says nothing about size. The missing axis: an audit batch earns its existence by deferring a systematic read too big to do inline. So even when a request is findings-shaped, /plan reads the artifact inline — surfacing and routing findings directly — when it's bounded and the findings are few; it queues an audit batch only when the read is large or systematic enough to need its own session. A user saying "audit this" does not force a batch: if the artifact is small, read it and discuss inline, and say that's what you're doing. The why: the audit batch exists to defer a read too big for the session, so for a small read the batch ceremony is pure overhead.
- One item at a time. Finish one before presenting the next.
- Read SPEC.md before proposing work. Don't queue contradictions.
- Process accumulated captures before new planning work.
- Never write batch entries to QUEUE.md without showing the exact text first — and the rule keys to the write, not to where you are in the loop: the message immediately before any QUEUE.md batch write must contain the entry text verbatim. Approval attaches to shown text, never to a described shape, so a recommendation — however concrete — is not a draft, and "I'll add a batch that does X" is not the entry. The reason: loop beats live in conversation memory and a compacted session loses them, but the write action is always visible, so keying the rule to the action holds even with no memory of which beat you're on.
- A recommendation is not a decision. A draft is not a written entry. Both need the user's call.
- SPEC is a normal doc any batch can edit — there is no separate spec-edit batch type. Which of three paths a SPEC change takes is set by where it's decided:
  - **Decided in /plan** — when a planning decision changes what SPEC says (a new capability, a scope change, a reworded rule — the test is whether any SPEC sentence goes wrong), edit SPEC in that same /plan session, with the user present and approving. Don't defer it to a separate batch.
  - **Discovered during a build** — when a /next build finds it needs a SPEC change, it asks the user, adds SPEC.md to its `Files:` list, and edits SPEC inline as part of the build (see next-build.md's scope-management rule).
  - **A large SPEC rework** — a normal build batch whose `Files:` list names SPEC.md, authored like any build.

  The why, and what it protects: spec-driven development's core contract is that any change altering behaviour updates the spec in the same commit (resources/research/spec-driven-development-edit-workflow.md). Two close-out spec-sync checks enforce exactly that atomicity — one at the /plan close (done-plan.md), one at the /done-build close (done-build.md) — so a session can never close with SPEC left behind. SDD does not require a spec change to be its own gated step, and the one-line-batch ceremony the old spec-edit type forced was pure friction. When a change touches no SPEC sentence (a refactor, a localized fix), none of this applies — it's just a normal batch.
- /plan resolves what it can in-session; capture is only for what it can't. Research, queue-wide cleanup (line-ref drift, quoted-string staleness after a sweep), cross-batch reconciliation, doc verification — anything within /plan's reach — gets done now, not filed for a later session. Reserve a capture for what /plan genuinely can't resolve this session: it needs data the session doesn't have, needs design discussion across sessions, needs user input not yet available, or surfaces a structural question whose answer would gate the work. This is a default, not an absolute — the test is "can /plan resolve this with what it has right now."

## Capture and parking discipline

The control rule for capture and parking, in one place. Pieces also appear in the steps and in plugin-behaviour.md; the canonical statement is here.

- **Two structural slots for items removed from active flow.** `Blocked by:` (trigger-based, auto-surfaces — slug plus optional behavioural prose tail) and `Parked:` (indefinite, conscious revisit only — short reason). Nothing leaves active flow without one. See plugin-behaviour.md Dependency ownership for slot semantics. Applies to batches in Batches Parked and captures in Captures Parked alike.
- **Processed/unprocessed split in Captures.** Captures is divided by `---`. Processed (above) have had dependency management applied at least once and carry slugs. Unprocessed (below) are raw appended in file order. Routing (promote/park/drop) is separate from dependency management — a capture can become processed in one /plan and routed in another. See Step 2 for the loop.
- **Routing gate before recommendation.** Step 2 sub-step 2 scans capture text for references to other items before the promote/park/drop recommendation, and classifies each by linguistic marker. Forward-looking language ("once X ships," "after Y," "depends on," "needs") is a dependency and defaults the recommendation to park-with-`Blocked by:`-populated. Backward-looking language ("observed at," "see," "surfaced during," "from") is an evidence citation, does not park the capture, and is named with its role at recommend time so a wrong call stays user-catchable. Ambiguous keeps the park default, the safe side. Classification is by marker, not prose-judgment of intent.
- **Filing-time blockers go in the slot, not the prose.** When the user files a capture and the blocker is already known, write `Blocked by: [slug] + condition` inline on the capture. /plan's Step 2 dependency scan picks it up mechanically rather than re-reading the prose. Stated in plugin-behaviour.md Captures.
- **Red flags route to the Red flags section, carrying a state — not promote/park/drop.** A capture (or an in-session observation) that records a security, privacy, or breach risk Claude surfaced — per the Red flags rule in plugin-behaviour.md — moves into QUEUE.md's Red flags section at the top, never into Batches. It carries one of three states: open, resolved, or accepted (defined in plugin-behaviour.md Flag states). The state can change as the risk is discussed — open → resolved when the risk is designed out or fixed, open → accepted when the user is told the risk plainly and chooses to proceed anyway. An accepted flag's decision is recorded in the session LOG at close (see done.md) — the informed-consent trail.

## Step 1: Read state and entry question

Read QUEUE.md and SPEC.md. Check whether Captures has items.

**Plan marker at the queue top.** If the top of Batches carries a `--- Plan session here: <reason> ---` marker, addressing its stated reason is part of this session's work — that's the planning the marker was placed to force. Handle it, then remove the marker once its reason is addressed so /next is no longer halted there.

**Unpark + staleness scans:** [SILENT] before the entry question, walk the active queue against plugin-behaviour.md Dependency ownership (Unpark watch + Staleness watch). For Parked items carrying a `Blocked by:` header: read the header as the primary surface — slug portions fire mechanically (if the named slug has shipped, the item is a candidate; verify against LOG/index.md), behavioural prose tails still need judgment. **Mixed trigger — check every slug even alongside a behavioural condition.** When a `Blocked by:` header names one or more slugs *and* a behavioural condition (e.g. `Blocked by: [slug-a] + [slug-b] + a few goal sessions run`), still check every named slug mechanically against LOG/index.md — don't read the whole header as behavioural and skip the slug check. If a named slug has shipped, surface the item as an unpark candidate for the user's judgment, regardless of whether the behavioural half is satisfied. The why: a mixed header once let a parked item sit for weeks though its blocker slugs had shipped, because the behavioural tail made the whole header read as a behavioural trigger and the mechanical slug check was skipped — the user had to raise it by hand. For Batches and Captures: anything stale enough that surrounding code or rules have moved past it? The scans' output is candidates feeding Step 2, not findings to narrate here — collect them silently and carry them into Step 2, where they're processed ahead of Captures (see Unpark candidates first). No silent edits: every candidate goes through the Step 2 loop, where the user decides.

**Parked-shelf review:** [SILENT evaluation; surface only the stale] Its own step, run every /plan read-state — give it the weight to actually run, not a clause to skim past. It covers only items marked `Parked:` (trigger-less); `Blocked by:` items stay out of it (they surface on their trigger, handled in the scan above). Read each `Parked:` item against whether the project has evolved past it. Evaluate every item silently and surface to the user only the ones you judge genuinely stale — never the whole list. Each stale candidate carries into Step 2 with the drop / rewrite / keep choice (per plugin-behaviour.md Dependency ownership Staleness watch). Anti-nag: skip any `Parked:` item already stamped `Reviewed <date>: keep` whose suppression interval hasn't elapsed and which carries no new staleness signal (see plugin-behaviour.md Dependency ownership). The why: the queue grows endlessly and an un-pruned parked shelf is a standing context cost paid on every read, and this scan is the only thing that ever asks whether a parked item still earns its place — burying it as a skimmable clause is what let 16 parked items pile up unreviewed (36% of the queue, more than the active batches).

**Deferred-test roll scan:** [SILENT] on the same pass, read QUEUE.md's Deferred tests section — verification waiting on an event, so the live question each session is which lines' events have now fired. Collect every line whose deferral may have cleared since it was written — host-side lines (once the plugin has been reinstalled; a private test-build reinstall is enough — only the external marketplace lines additionally need a push to the remote), external lines (once their event occurred) — together with any already-runnable user-run or Claude-runnable lines, and carry them into Step 2 as one combined move, not per-line interviews. A line's runnability is read from the requirement it names — a user-run line names what it needs (the terminal, a device, an eyeball on the screen), and that requirement, not a guess about the user's setup, is what classes it user-run. Still collect the host-side lines; whether they've cleared is resolved in Step 2 by comparing the installed host's build stamp (surfaced at session start) against the target's current stamp, not by asking the user. Lines whose deferral plainly can't have cleared yet stay where they are.

Ask [PROMPT]: "Anything to discuss before we process Captures?" (If Captures is empty, ask what they'd like to work on.) Keep the question clean — no scan candidates folded in; they surface only inside Step 2.

**If the user has something to discuss:** Handle it via the Step 2 loop — present, interview, recommend, wait, execute. Then ask [PROMPT]: "Anything else before Captures?" Repeat until there's nothing more.

**Then process Captures:** Move to Step 2. Processing Captures is where every /plan session goes — a discussion item is just an optional first stop, never an alternative to it.

## Step 2: Process captures [SEQUENCE]

**Planning state file: _plan.md.** When capture processing begins, create `_plan.md` to hold this session's planning state: the carried unpark and staleness candidates, the item list, the current item, and the beat reached. Update it at each beat transition, and append each routed item with its disposition — promoted, parked, or dropped, with slug. One line per item, so updates stay cheap. The reason it exists: the file survives compaction, gives an interrupted /plan a resume path through session start, and hands /done a mechanical record of what was routed where instead of a reconstruction from memory. /done reads it at close and deletes it — same lifecycle as _build.md.

**Captures structure: processed/unprocessed split.** Captures is divided by `---` into processed (above) and unprocessed (below). Processed = /plan has applied dependency management at least once (given a slug, set a `Blocked by:` header, or confirmed standalone via Step 2 sub-step 2). Processed captures carry slugs so they can be cross-referenced. Unprocessed = raw appended in file order — no slug, no dependency headers yet. The divider is staging between raw and routed (promote/park/drop), not a final home — captures sit above it until routed out of Captures entirely. Routing is separate from dependency management and can happen in any later /plan: a capture can become processed in one session and routed in another.

**Unpark candidates first.** Candidates carried in from Step 1's scans are processed before Captures — Parked items have been waiting longest. Each enters the loop below as if it were a capture, sourced from Parked instead of Captures, through the same sub-steps (present + interview, recommend, execute, remove, checkpoint). The recommend options are the same three, reread for items already in Parked: **promote** means move out of Parked into Batches as a full batch entry, **park** means keep parked, **drop** removes the Parked item entirely. Staleness candidates take the same path with the Staleness watch's choice — drop, rewrite, or keep (per plugin-behaviour.md Dependency ownership).

**Deferred-test roll (one combined move).** The deferred-test lines carried from Step 1's roll scan are processed as a single move — counted as one item in the Step 2 count, not one per line. Resolve which deferrals have cleared: for host-side lines, compare content stamps — don't ask the user what's installed, and don't compare version numbers. The session-start hook surfaces the installed host's build stamp (a content hash of the installed plugin's own files). Compute the target's current stamp the same way — run the session_start hook's `content_stamp()` over `plugin/si-plugin/` — and compare the two: stamps match ⇒ the installed host carries the latest files, so all host-side changes are live; stamps differ ⇒ the host hasn't been reinstalled since the most recent host-side change, so they're not live yet. Stamp, not version, because a build batch edits host-side files (a hook, a procedure doc) without bumping any version and the `-testN` suffix only moves on a rezip — so the installed host and the target can show the exact same version while the host is missing the latest changes; the stamp asks the real question (do the files match?) and also catches the rebuilt-but-not-reinstalled case a version comparison misses. For external lines, the outside event is the one thing the version and the stamp can't tell you, so confirm those with the user (did the event occur?). For the lines that have cleared, offer to roll the user-run ones into a test batch (or attach them to a test batch being planned this session), and note that the Claude-runnable ones will be confirmed by observation in the next session that exercises them — they don't need a user-run test batch. Lines whose deferral hasn't cleared stay in the section untouched. This resolution is the point of the scan: nothing else checks whether a host-side line has gone live, so a silent skip leaves runnable tests sitting indefinitely — the failure this fixes.

When you surface a user-run or external line to the user, explain it in plain language — don't just name the slug. Say what the test checks, what it requires (the requirement named on the line — "needs the terminal," "needs a phone connected," "needs you to look at the screen"), and why Claude isn't running it itself (the requirement is the user's to meet, not something Claude can reach). Classify the line by that named requirement, never by an assumption about how the user works: a user-run line is the user's to run because of what it requires, and the user is the one who knows whether that requirement is theirs. The why this matters: a test handed over as "yours to run" with no explanation — or worse, handed to a user whose setup can't meet the requirement at all — reads as confusing or impossible; naming the requirement lets the user judge it, and naming why Claude can't run it keeps the handoff from looking like Claude shirking.

Candidates from Step 1 first, then captures in file order, top to bottom across both halves — unprocessed below the divider, then continuing into processed above it. State the count upfront, counting candidates and captures together ("5 items. First: ..."). (Processing follows the file as placed, not strict age: a capture placed next to its relatives jumps the age queue by design. Oldest-first is only the append fallback at filing time.)

For each item:

1. **Present and interview** [DISCUSS, PROMPT] — The item's verbatim text lands on its own beat before analysis begins. For **every item after the first**, it was already sent at the end of the prior item's checkpoint, so this beat opens directly with analysis — no re-quote, and no "my read to follow"-style pre-framing of any kind. For the **first** item there's no prior checkpoint to have carried it, so quote it at the loop's opening as its own beat and end that message on a brief, bold closing prompt inviting the user to continue — don't let the message trail off on the raw quote with nothing handing the decision back. The analysis then opens the next turn, with the turn boundary as the separator, exactly as it works for later items. Why the verbatim lands on its own beat, ahead of analysis: the user takes the item in more easily when they can read the raw text before Claude's framing arrives, rather than digesting the whole reaction the moment it lands bundled. Moving the verbatim to the prior checkpoint makes this structural — the turn boundary, with the user's reply between, is the separator by construction, so the old bundling-vs-forced-wait balancing act no longer has to be held in the moment. When quoting the first item, the separator that forces the quote out as its own beat is the re-read: after the quote goes out, re-read the item from QUEUE.md to confirm the quoted text matches the file, which also catches a context-drifted quote before it's discussed (if the file differs, correct it immediately). For later items that re-read already happened at the checkpoint that presented them. Engage with the item's substance: ask follow-ups to sharpen it or surface missing context, depth scaling with the item, until the picture is clear. Close the interview: when a park or drop lean is already clear, close on the combined recommend-and-ask in sub-step 3's merge guidance — not a bare "anything else to add?" trailed by a separate recommend turn; when the lean isn't clear yet, close with "anything else to add?" and let sub-step 3 carry the recommendation. Unpark candidates enter this loop the same way.

**View-in-doc: pointer instead of paste when an editor is recorded.** The verbatim item lives in QUEUE.md already, so re-pasting it into chat spends tokens on text the user can open in their own editor. Check CLAUDE.md for an `Editor:` field with a real value (any value other than `not recorded` or an absent field). When one is recorded, render the first item's own beat as a one-line pointer that names the item and links to the doc, instead of the pasted quote — for example: `First capture — **[capture-slug]** — is in [QUEUE.md](QUEUE.md) under Captures.` Still end that message on the same brief, bold closing prompt handing the decision back, so the beat lands rather than trailing off. The confirm-against-the-file re-read still runs, in its pointer form: re-read the item from QUEUE.md to confirm it's there and the pointer resolves (there's no quoted text to drift now, so this is a resolves-check, not a text-match). When no editor is recorded, keep the verbatim inline quote exactly as above — the pointer is the token-saving path, the inline quote the safe default.

2. **Dependency scan** [SILENT] — Before recommending, scan the capture text for references to other items (slugs in `[brackets]`, bold titles, named work) and classify each by the language that frames it, not by guessing intent:
   - **Forward-looking** ("once X ships," "after Y has run," "depends on Z," "needs W") — a dependency. The default recommendation in sub-step 3 becomes park-with-`Blocked by:`-populated.
   - **Backward-looking** ("observed at," "see," "surfaced during," "from") — an evidence citation, not a dependency, so it does not park the capture. The capture-authoring standard asks for origin and reasoning, so evidence citations are common; a citation must not block the work it cites. When a reference is classified as evidence, sub-step 3's recommendation names the reference and its role (citation), so a wrong classification stays catchable by the user.
   - **Ambiguous** — keep the park default, the safe side.
   If no reference is found, give the capture a kebab-case slug (if unprocessed) — it's now processed and stays above the divider whether or not it gets routed this session. Classify by linguistic marker, not prose-judgment of intent.

3. **Recommend** [PROMPT] — Recommend a route — promote, park, or drop, or (for a red flag) move it to the Red flags section — and say why:
   - **Promote** — ready to become a batch. The recommendation must describe what would actually get built, in terms the user can recognize as the work product (which files change, what subsection or rule, what gets added/removed/rewritten — not just the topic or intent). Forcing function: if sub-step 1's interview hasn't yielded enough to describe the outputs concretely, the recommendation isn't ready — return to interviewing. **Trace dependencies (build batches):** before recommending promote for a build batch, trace it per Step 3's Trace dependencies — read the named files plus the relevant SPEC, surface any dependency the capture didn't name, run the shared-primitive scan, and confirm every dependency has a producer; name any missing-producer hole. Carry the trace evidence into the rationale you draft in sub-step 4. **Downstream-impact scan:** if the capture installs a *structural rule* (defines what something is, sets a constraint that frames how other captures get evaluated — as opposed to a localized fix), scan the remaining Captures for items that could revise or invalidate the rule. Trigger is rule shape, not edit size. If any are found, flag at recommend time, name the conflict, and offer three options — process the downstream capture first, hold this one, or proceed accepting the possible later revision.
   - **Park** — not now, keep for later. If sub-step 2 found a dependency, this is the default and `Blocked by:` is populated from the scan. Otherwise park with a short `Parked:` reason.
   - **Drop** — remove it
   - **Red flag** — the item records a security, privacy, or breach risk Claude surfaced (per plugin-behaviour.md Red flags). It routes to the Red flags section with a state instead of becoming a batch — see Capture and parking discipline. Recommend its state: open if unaddressed, resolved if the discussion designs the risk out, accepted if the user is told the risk plainly and still chooses to proceed.
   Stop and wait. The user decides.

   **Fold the recommend into the action when the user already agreed during the interview.** When present-and-interview already secured the user's explicit agreement to a specific route — Claude gave its lean and the user said to go with it — skip this standalone recommend-and-wait and go straight to the action in sub-step 4, naming the route in one line ("going with promote — drafting now"). This fold is scoped to **promote** only: promote is followed by the draft-approval step, which the user still owns, so folding loses no decision — the draft is the safety net. **Park** and **drop** can't fold to the action — they are terminal, with no later approval step to re-confirm them, so the user's explicit approval is still required before execution. But that approval doesn't need its own separate turn: when the lean is already clear it merges into the interview-closing turn (next paragraph). The fold fires only on explicit in-interview agreement to a specific route; an open or ambiguous interview runs the recommend-and-wait above. The why: re-asking a decision the user already settled adds a round-trip without adding judgment, and the promote draft-approval is exactly why promote can fold while park and drop cannot.

**Merge a clear park/drop recommend into the interview-closing turn.** When a park or drop lean is already clear by the end of the interview exposition, don't close with a bare "anything else to add?" and then re-state the recommendation in a separate turn — that names the route twice with a content-free exchange between ("my lean is park" → "anything you'd change?" → "Recommending park. Park it?"). Instead, close the exposition on one combined, bold ask that carries the recommendation: "…my recommendation is park; anything you'd change, or shall I park it?" The user pushes back or approves in a single reply, and that reply is the terminal approval park and drop require — so merging loses no decision, it only drops the empty middle turn. The standalone recommend-and-wait above stays the path when the lean genuinely isn't clear yet at the interview close. Promote is unchanged: it folds to its draft (the previous paragraph), and the draft-approval remains its safety net.

4. **Execute promote, park, drop, or red-flag routing:**
   - **Promote** [DISCUSS, PROMPT] — Draft the batch entry (bold title, prose rationale, Build/Test subheadings). The rationale carries the discussion's reasoning as inline prose — see Why-pipeline in plugin-behaviour.md. Show the draft as a blockquote with a content-type lead-in (**Batch draft:**), per the approval-time outputs rule in plugin-behaviour.md. Don't write to QUEUE.md until approved. Claude places the batch using dependency ordering and reports where it went.
   - **Park** — Move to Parked with the `Blocked by:` or `Parked:` header populated per sub-steps 2 and 3.
   - **Drop** — Remove. If already decided (check LOG/index.md), state the prior decision and commit.
   - **Red flag** — Move the item into QUEUE.md's Red flags section at the top, written with its state (open, resolved, or accepted). When the state is accepted, done.md records the decision in the session LOG at close — what the user was warned about and that they chose to proceed.

5. Remove the item from Captures once routed (promote, park, drop, or moved to the Red flags section). If only dependency management was applied this turn — slug given or `Blocked by:` set without routing — the capture stays in Captures but moves above the divider as a processed item; don't remove it.

6. **Checkpoint** [PROMPT] — After every item, present the next capture and then close on the off-ramps as the message's final, bold ask. Order within the message: when a next capture is queued, lead with that capture's verbatim text — the item only, no analysis — re-read from QUEUE.md first to confirm the quote matches the file (the confirm-against-the-file re-read lives here, not in the next item's present-and-interview beat); then, below the verbatim, put the three off-ramps as the closing bold question — continue to the next capture, close out now (go to Step 4), or raise something else (loop back into Step 2 with the new item). All three must be genuinely on offer; deliver them conversationally rather than as a fixed form, but they land below the verbatim, not above it. The verbatim is shown, then the ask hands the decision back — putting the ask last gives the message a proper landing instead of ending on a raw quote that reads as Claude stopping mid-thought. Why the verbatim still leads rather than the analysis: it lands the next item this turn so the user reads it before deciding, and when they continue, the next turn opens directly with analysis — the turn boundary is the separator. The verbatim shown here is that next item's own presentation, not a forbidden look-ahead: the user acts on it immediately (it is the very next thing processed), so it is not a [SEQUENCE] violation — the forbidden case is teasing items the user must hold in their head while still working the current one. Wait for the user's call. On the last capture there is no next verbatim to show, so the message is just the off-ramps as the bold ask, with "continue to the next" dropping out naturally — the offer becomes the remaining two.

**View-in-doc applies here too.** When CLAUDE.md records an `Editor:` field with a real value (per sub-step 1's check), lead the checkpoint with a one-line pointer to the next item in the doc — `Next capture — **[capture-slug]** — is in [QUEUE.md](QUEUE.md) under Captures.` — in place of that item's pasted verbatim, then put the off-ramps below it as the closing bold ask, unchanged. The re-read still runs in its pointer form (confirm the item is there and the pointer resolves). When no editor is recorded, lead with the verbatim exactly as above.

After all items: Captures should hold only processed items above the divider (or be empty if everything was routed). Section header, divider, and `### Parked` intact.

New items from conversation follow the same loop — check QUEUE.md for overlap first.

If Claude notices a gap: "I notice [X] — want to hear a suggestion?"

**Wind-down re-scan** [DISCUSS, PROMPT] — After every capture is processed and before recommending /done (the Step 4 close-out), re-read this session's own discussion and surface candidate captures: things the user thought out loud but never explicitly flagged. Name the step's own best-effort nature in plain words when it runs — it re-reads whatever conversation is still in view, and a long session may have lost earlier discussion to compaction — so a surfaced-nothing result isn't read as "nothing was missed."

Present all surfaced candidates as ONE numbered set of fully-drafted captures for a single approval: the user contests by number, and only contested items are then taken one at a time. This is the bulk-approval inversion in plugin-behaviour.md's [SEQUENCE] rule — the re-scan is a result set produced under an understood criterion (like audit findings), so per-item approval would add round-trips without adding judgment the bulk view doesn't already give. Approved candidates are filed to Captures; routing them (promote / park / drop) follows the normal capture flow, this session or a later /plan.

The why: this is a best-effort safety net behind the capture-at-the-moment-of-noticing rule, memory-dependent so degraded after compaction. A non-coder who thinks out loud generates capturable material they never explicitly flag, so the re-scan catches what the moment-of-noticing rule outran. The find-then-sharpen flow here is planning work, and /plan is the only skill that processes captures and has the most free-form discussion — so /plan owns the full re-scan: it both files the surfaced captures and carries them into routing. But the *filing* half is not /plan-exclusive: /done runs a file-only version of this same re-scan at its close (see done.md's Wind-down re-scan section), because filing captures is allowed in any session. What stays /plan-only is *routing* the surfaced captures — promote / park / drop — which is the planning the no-planning-in-execution rule protects. So /done may surface and file what the session thought out loud, and leave the routing for a later /plan; the earlier "/done is deliberately not a home" stance is replaced by this file-only carve-out.

## Step 3: Batch structure

```markdown
**Batch title** **[batch-slug]**
Depends on: [other-slug], [other-slug]
Blocks: [other-slug]

[Prose rationale — one or more sentences. What motivated this work, what's broken or missing, what changes once it lands.]

Build:
- What to build (a build that changes SPEC lists SPEC.md in Files and says which sentences change)

Test:
- How to verify

Audit:
- Target: which docs, files, or area to review
- Criteria: what to look for (repetition, drift, tag misuse, prose-where-tag-belongs, etc.)

Freeform:
- What the work is, and one line on why it's not a build, a test, or an audit
```

Bold title with a stable kebab-case slug appended as a `**[slug]**` marker, then optional `Depends on:` / `Blocks:` header lines (omit either when empty — no `Depends on: none` placeholders), then the prose rationale, then entries under Build, Test, and/or Audit subheadings. See plugin-behaviour.md Dependency ownership for the slug and header rules. Each entry names its own target. The rationale is inline prose (no `Why:` label, no separate field) and carries the reasoning forward — /next copies it to _build.md, /done re-authors it into the LOG entry. See Why-pipeline in plugin-behaviour.md.

**SPEC changes are normal build scope.** SPEC.md is a normal doc any batch can list in its `Files:` — there is no separate spec-edit batch type. A batch that will change SPEC names SPEC.md among its files, and its Build entries say which SPEC sentences change and to what, alongside any other build work. The scope-lock allows SPEC precisely because the batch lists it. A SPEC change a *planning decision* makes is edited in the /plan session itself (Ground rules), not queued as a batch. A change a *build* discovers it needs mid-session is added to scope then — the build asks the user and adds SPEC.md to its files (next-build.md). A large SPEC rework is a normal build batch that lists SPEC.md. There is no hybrid to forbid and nothing to split: a batch that touches SPEC and other files is fine, because the close-out gates catch drift rather than a batch boundary forcing the separation. The why these gates replace the old spec-edit batch: SDD requires the spec to move in the same commit as the behaviour change, which a commit-boundary gate enforces directly (the /done-build spec-sync gate, done-build.md; the /plan-close spec-sync gate, done-plan.md) — the old batch added a whole /next cycle to change one line and protected nothing the gates don't.

**Freeform batches.** Freeform is the home for planned work that isn't a build, a test, or an audit — an ad-hoc change, a discussion of edits already made, something to surface without the pressure of processing it. When scoping a Freeform batch, run the same gate the on-demand `/next freeform` runs: could this work be a build, a test, or an audit instead? Those three have homes already, so freeform is only for what fits none of them. The entry carries one line naming why none fit — that line is the gate's answer, written into the batch so /next inherits it. Freeform scope is granted ask-by-ask during the build, so its entries needn't name files; the lock starts at method-docs-only.

**Build entries name their files.** A build entry names the files it touches — the scope-lock's `Files:` list in _build.md is populated from those names, so build scope gets decided here at planning time instead of ask-by-ask during the build (see plugin-behaviour.md Scope). A file that doesn't exist yet counts as named when the entry says what gets created and where. A batch whose entries name no files to edit (audit batches, test-only batches) leaves the lock at method-docs-only.

**Trace dependencies (build batches).** Before a build batch is ready, trace its dependencies rather than asserting them from surface reasoning. Read the files the batch names plus the relevant SPEC, derive the real dependencies — surfacing any the batch didn't name — and run the shared-primitive scan: does another queued batch need the same underlying mechanism? If so, chain or merge them rather than building it twice. Confirm every dependency has a producer — a queued batch, shipped work (LOG/index.md), or existing code/SPEC; a need with no producer is a missing-producer hole, so name it for the user. Record where you traced — which files, which SPEC sections — in the batch rationale; the `Depends on:` line stays clean slugs. One line does it, e.g. "Traced against next-build.md's scope-lock step and SPEC's scope paragraph; producer is [scope-lock-core] (shipped); no shared primitive with other queued batches." See plugin-behaviour.md Dependency ownership (Dependency tracing) for the canonical five obligations and the accepted limit. Build batches only — test and audit batches skip this.

**Think through testing when drafting.** Before authoring the Test section (or deciding to omit it), sort each test this batch needs into one of three categories — this is the canonical statement of the test routing the whole method uses:

1. **Run-now (inline).** Any test Claude can run this session — read files, run commands, trace logic, inspect output. This is the default, and it includes environment-dependent tests when the environment is actually available (a connected device, a running emulator). Most tests live here.
2. **User-must-run.** A check whose *requirement* only a person can meet — a visual or subjective judgement (looking at a screen), a physical action (tapping through an app, connecting a device), or a tool Claude can't drive (a separate terminal). Classify it by what it requires, named plainly on the line ("needs you to look at the screen," "needs the terminal," "needs a phone connected"), not by an assumption about how the user works. The why: Claude rarely knows the user's environment, so a rule that rests on detecting the user's workflow doesn't generalize — but a test's requirement is always knowable, and the user knows whether that requirement is theirs. Handed over in the session that needs it.
3. **Claude-run-but-environment-dependent, or host-side.** A test Claude would run itself but that needs a device, emulator, or environment not present this session, or that awaits a push + reinstall → defer until runnable.

The spine: run-now is the default; defer is the exception, justified only by category (2) or (3), never a catch-all for "can't run this second." Before assigning a test to (3) because the environment is absent, confirm it really is absent — ask the user whether a device or emulator is available rather than assuming, and ask permission before using one (see [ask-before-device-use] and plugin-behaviour.md Device and hardware access). The reason this needs naming: category (3) is the one that gets abused — a runnable test gets parked as "can't run now" and sits unrun for weeks, when it could have run the session it was written.

These categories use the same vocabulary as the two-axis Deferred tests tags ([deferred-test-seams-fix]), so the two don't drift: a deferred category-(2) test is runnability user-run; a deferred category-(3) test is runnability Claude-runnable (Claude runs it once the environment exists), with deferral reason host-side (awaits reinstall) or needs-user (awaits a device the user connects). Every deferred line also keeps its source batch slug, so a later session running the test traces it back to the batch that planned it — the why-pipeline trace survives the deferral.

Populate Test with what you find — or proceed without one when the change is self-verifying from the build entries. The decision to omit gets made consciously, not by inattention.

**A user's eyeball-review of generated output is a review, not a test.** When a batch's only verification is the user reading generated output to judge it — a written doc, copy, a drafted section, anything human-readable the build produced — that's a review, not a pass/fail test. Don't author it under Test, and don't dress it in test or pass-fail language. Note it plainly as a user review (e.g. "the user reads MAP.md and says if anything's off"). The obligation to actually look still stands — it just isn't a test, so it isn't tracked with the test machinery. A genuine behaviour-verification (does the thing work when exercised) still goes under Test as now. The line: a test checks behaviour against a definite pass/fail; a review is a person judging generated writing, which has no checkbox. This pairs with done-build.md's close framing and done.md's Deferred tests carve-out.

**Test section:** Only when there's a behaviour to verify that isn't self-evident from build entries. Not every batch needs one — but /done doesn't generate tests, so anything needing verification must be planned here. [SILENT] when omitting — the rationale already tells the user what kind of change it is.

Split test entries by who runs them, per the thinking above. Write each so /next knows which kind.

**Roll in deferred tests.** When authoring a test batch, check QUEUE.md's Deferred tests section for pending Claude-runnable or user-run lines that can ride along, and move each rolled line out of the section into this batch's Test entries. This is the execution channel for the Step 1 roll scan — the deferred backlog reaches a runnable session through a test batch, not through a separate listing.

**E2E tests get their own batch.** User-run E2E tests (separate project, live session) don't go in build batches — they'd block the build flow.

**Readiness gate** (per batch): can you write the candidate index entry now — artifact touched + nature of the change, per plugin-behaviour.md Index entries? If yes, the batch is ready and the entry can be pre-generated for /next to carry into _build.md. If no, the batch isn't coherent enough yet — keep interviewing. Matching scope check: can the `Files:` list be populated from these entries — does each build entry name the files it touches, or consciously name none (audit and test-only batches)? If the files can't be named yet, the entries aren't concrete enough — keep interviewing. **Trace gate (build batches):** a build batch isn't ready until its dependencies are traced and every one has a producer (Trace dependencies above). An untraced build batch, or one with a missing-producer hole still open, isn't ready — trace it, or surface the hole, before it goes in.

**Audit batch sizing gate:** for audit batches, the readiness check is whether target and criteria are specific enough that Claude can write the audit prompt without further dialogue. If the target is vague ("the docs", "the UI flows") or the criteria open-ended ("anything off"), keep interviewing until both pin down.

**An audit batch routes findings to Captures only — author it that way.** An audit's whole product is findings appended to Captures, which /plan and the user then vet. So when authoring an Audit batch: name no write-target doc in its Files, and set its Output to route findings to Captures — never an Output that directs a write into a named document. When the real deliverable is a written document — a findings report, a summary for someone outside the project — that document is a *build*, authored after the findings are vetted: the flow is audit → Captures → /plan → a build batch that writes the doc. The why: an Output pointed at a doc-write skips exactly the vetting the route-to-Captures contract exists to force, so a finding lands durable before anyone has checked it. If a batch's intent is a durable findings doc, author the audit now and queue the doc-writing build after this audit's findings reach /plan. Worked slip to avoid: an Audit batch named a findings doc in its Files and set an Output of "append candidates to" that doc — that is a feature build wearing an audit's label; split it into the audit plus a later build.

**Ordering:** Claude places by dependency where applicable — dependencies first, then scaffolding, features, polish. Oldest-first is the fallback when no dependency applies (per plugin-behaviour.md Captures placement). Either way, Claude reports placement and reasoning per Dependency ownership narration — including the explicit "appending here because no dependency applies" case.

**Plan markers — write predictable planning moments into the queue.** When placement creates a spot where a planning session must happen before /next can continue, insert a marker line between the batches at that spot: `--- Plan session here: <reason> ---`, with the reason stated inline. Two cases illustrate when (not a closed list): an audit batch sits ahead of batches that depend on its findings, so those findings must be processed in /plan before the dependent work can be scoped; or a batch's dependencies wait on a design question no planning session has answered yet, so /plan must settle it first. The marker converts a judgment-based "you should run /plan around here" into a mechanical gate /next halts on — the same shape as the push marker. It's a floor, not a ceiling: planning must happen here at minimum, for the stated reason; ad-hoc /plan anywhere else stays unrestricted.

## Step 4: Close out [BRIEF, PROMPT]

**Check the dependency graph before closing.** [SILENT] when it's coherent; surface and wait [PROMPT] when it isn't. Re-read QUEUE.md and walk the graph once, confirming three things:
- **Ordering:** every `Depends on:` slug sits *above* its own batch in Batches — or has already shipped (check LOG/index.md) or is otherwise satisfied. A batch ordered ahead of something it depends on is the out-of-order break /next trips on.
- **Resolution:** every slug named in any `Depends on:`, `Blocks:`, or `Blocked by:` header resolves to a real item — a batch in Batches, a parked item, or a shipped slug in LOG. A header pointing at nothing is a dangling reference.
- **No dependency on an unprocessed capture:** no batch depends on a capture still sitting raw below the Captures divider. A `Depends on:` slug that resolves only to an unprocessed capture is dangling until that capture is processed and promoted — the missed-capture case (clearing every capture is the user's discipline, and a miss leaves the link hanging).
- **Producer existence (build batches):** each build batch's declared dependencies has a *producer* — something that actually builds the need: a batch above it, shipped work (LOG), or existing code/SPEC. Ordering and resolution check that the declared slugs sit right and point at a real item; producer-existence is the trace's completeness check (plugin-behaviour.md Dependency tracing) reaching the close — it confirms nothing a batch genuinely needs was left with no producer at all. A dependency resolving only to a parked or indefinitely-blocked item is a missing-producer hole, because that item won't build the need in the queue's current shape. Surface any hole before closing.

Coherent graph: say nothing, go straight to the close line below. Broken graph: don't close clean. Name what's broken in plain words, fix it in-session with the user's approval — reorder the out-of-order batch, or return to processing the missed capture (the Step 2 loop) — and narrate what was caught. Example: "One thing before we close — [batch-a] depends on [batch-b], but [batch-b] sits below it, so /next would reach [batch-a] first. Move [batch-b] above it?"

The why: /done is the first skill that actually walks this graph today, so a break sails through /plan untouched and only bites at /done — forcing a /plan re-run. Checking it here, in the skill that owns ordering, closes the gap before the handoff. The mechanical lint [plan-close-dep-lint] is the sibling net. Scope: every /plan close.

**SPEC in sync before closing.** [SILENT when in sync; surface and fix when not] If a decision this session changed what SPEC says and SPEC wasn't updated in-session, catch it now: update SPEC with the user's approval before recommending /done. This is the obligation the /done-plan close enforces as a hard gate (done-plan.md) — surfacing it here means the close stays clean rather than stopping. The why: SDD atomicity — the spec moves in the same commit as the decision that changed it, and this in-session edit is what the retired spec-edit batch used to carry. Scope: every /plan close where a product-truth decision was made.

**Position the readiness line.** [SILENT when its placement is unchanged; BRIEF when it moves] Before the close line, place or move the `--- Cleared to run above this line ---` marker in Batches so everything above it is cleared to run and everything below isn't yet. A batch is cleared when it meets the [dependency-tracing-pass] readiness definition: traced, complete (every dependency has a producer), correctly ordered, and not still exposed to a raw capture below the divider that could change its dependencies. Walk Batches top-down and put the line just below the last batch that meets all four; the first batch that fails any of them — and everything after it — sits below the line. If every batch is cleared, the line goes at the bottom of Batches; if none is, at the top. Narrate where it lands **only when it actually moves** this close — one plain line, e.g. "Top three batches are cleared to run; the line sits above [batch-x], whose dependencies aren't settled yet." When your walk confirms the line is already correctly placed and nothing moved it, confirm silently and say nothing — mirroring the dependency-graph check above, which stays silent when the graph is coherent. This is the boundary the user would otherwise have to work out by hand each session, and the unattended build mode later inherits it as its run bound. Scope: every /plan close; narrate on move, silent when unmoved.
