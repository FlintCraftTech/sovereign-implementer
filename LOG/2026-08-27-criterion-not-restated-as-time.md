# beac9d2 — A readiness criterion may not be restated as a calendar claim

Twice in one planning session a criterion was announced as a time. A readiness test of "one plan run and one next run" was reported as "nothing goes up today" — when both sessions could perfectly well run the same day. The user caught both, and settled it in four words: *"There's no timing to this."*

The rule: when saying when something can happen, state the criterion and check the world against it. Reach for "today", "tomorrow" or "later" only where the criterion **itself** is a date.

**Written as one clause on the rule that already governs this**, not as a new rule. The always-loaded date rule already says to read a computed field rather than deriving today's date by assumption; this is the same subject one clause wider — the first arm stops a date being invented, the second stops a non-date being converted into one. Same failure, same paragraph, no new slot.

**Why the conversion is worth a rule at all.** A time claim reads as a fact about the calendar and is acted on as one, so it moves a decision the criterion never licensed — in the recorded instance, deferring a post by a day for no reason that existed. And like a wrong date, it reads exactly like a right one for as long as it stands: nothing downstream can tell that "today" was substituted for a condition nobody checked.

Admission rests on two recorded failures in one session, both caught by the user rather than by any check.
