# SPEC — Throughliner

## What this is

A Claude Code plugin for non-coders. It gives users a structured workflow for building apps with Claude Code without needing to know how to code.

**Its distinctive value, and the thing it is named for: the user's intent keeps running the project whatever Claude remembers.** Claude Code now carries some memory of its own between sessions — private notes and summaries the user never sees or approves, kept lossily and on no schedule the user controls. The **throughline** is different in kind, not just in durability: a structured, user-vouched record of *why*, carried as prose from a captured idea, through the work item, into the session record — so any session, including a fresh one carrying nothing forward, still builds the project the way the user meant instead of re-deriving intent from the code, or from Claude's own unvouched notes, and guessing wrong. That is the product, not a side feature; framing it as occasional why-lookup is what makes the approvals and the log-writing look like pure overhead.

**The throughline is the reasoning spine, and it is not any single file.** Intent lives in SPEC, rationale rides every QUEUE item, history lives in LOG. SPEC and QUEUE are read *during* planning and building, so the throughline shapes every plan and build silently rather than only on a "why?" query; LOG is the deep archive, pulled on demand. **LOG records the throughline and is not itself the throughline** — the tell is that a complete LOG can carry no throughline at all, every event recorded with the reasoning stripped out, which is exactly the failure the mechanism fights.

**The stance it takes: Throughliner dials human intention up to the maximum.** The person directs the work and the record is theirs to read and approve; the tool's job is to carry that intention forward, not to substitute for it. It is one answer rather than the only one — more agentic approaches, which hand more of the direction to the model, are a different and legitimate choice.

**What it is worth to Claude:** it is how Claude stays aligned to intent — not just to *what* the user wants but to *why they want it that way*. Rationale is what stops a settled decision being reopened: a rejected option carries the reason it lost, so it is not proposed again. And recorded intent is what makes a contradiction visible at all, so drift can be caught.

**What it is worth to the user:** settled things stop being re-decided, because a rejected option's reason for losing is recorded and so is not re-proposed; silent regressions are prevented, since the reason a thing is the way it is can be read before changing it; institutional memory survives a break or a handover; a growing project stays coherent instead of rotting; and the project can be trusted to still reflect intent rather than depending on Claude remembering it.

**The perceived overhead is reframed rather than denied.** The approving is what makes the record genuinely the user's and therefore trustworthy — a reason they never vouched for is one they cannot trust on read-back. The log-writing pays a small cost now against the large "why did we do this?" cost later. And externalised intent is exactly what lets short, cheap sessions work at all.

**In user-facing help, the work-flow and the throughline are two separate beats.** How work moves — captured, processed, built — is the work pipeline. The throughline is the *why that travels alongside it* and survives Claude forgetting. Explaining them as one thing collapses the distinction.

## Who it's for

Non-coders who know what their app should do but need a framework to keep Claude aligned.

**Projects where most of the work is the user's own are in scope, not an edge case.** Throughliner governs work wherever it is conducted — not only work that touches the machine. In some projects Claude builds nearly everything; in others Claude only partly implements, or barely at all, and the tool serves as an executive layer over the user's own work: the queue is the to-do list, `[user]` items carry the steps with their walk-throughs, and the throughline keeps the why alive across sessions exactly as it does for code. Sometimes the user does not want to complete things in conversation — they want the list. That is a supported way to run a project, not a degraded one.

**A session may hold more than one person, and the queue's two sections are the trust boundary.** Anyone present may file captures — the unprocessed section is un-vetted by design, so participant ideas land there safely — while the decisions the method assigns to "the user" (processing an entry into Processed or deleting it, expanding a build's scope, clearing a risk, approving anything that leaves the machine) belong to the one person holding execution authority. Moving an entry into Processed is itself a state change: it authorizes an unattended build, so approval authority attaches there, not only at file edits. Where the channel people arrive through authenticates them — a chat server whose members carry a role attesting a real GitHub login — identity is the authenticated identity the channel supplies; where it doesn't, a named person's word is the fallback and is read as such. Credit follows the named person whose message raised an idea, under the same tests that govern a single user — agreement is not authorship — and a commit may carry co-author credit for a participant, using only details they have chosen to share.

**It is built for someone who wants a record they can trust and return to** — next week, after a break, when something looks wrong. Approval happens in conversation, in plain words, and the record is what that conversation produces; a user who never wants a readable record is considered but is not the target. **Length is the thing that has to be earned**: an artifact that outruns what a person will get through is the tool's failure, not the reader's.

**Every written shape carries a bound: the median of that shape in the project's own measured distribution.** `scripts/measure_written_shape_length.py` prints the current figure for captures, work items, session records and index lines. A median is a proportion of the corpus rather than an invented number, so it is derived rather than asserted, and it ratchets — writing to it pulls it down.

**Both failures are real.** A record too thin to rebuild intent from has failed as surely as one too long to get through. The second is the one this method has produced at scale, which is the direction the bound binds in.

## How it works

Splits changes into a build queue that helps the user harness Claude's skills in dependency management, not just coding. The secondary core functionality is basic context window management.

Five skills drive the workflow:
- `/setup` — scaffold project docs and run the onboarding interview.
- `/plan` — manage the queue, add ideas, resolve questions, check for drift. It opens by running a mechanical digest of the queue **and then reading the whole file** — the digest for the facts only a script can compute, one line per queue entry, and the file for the rationale prose the digest deliberately omits. Both, because they carry different things: how long an item has been held, where a named blocker sits, which files two items both name and whether an item's premise cites work that has shipped cannot be got by reading, while an instruction one item carries about another's ordering lives in prose and appears on no digest line. For a period the digest replaced the read, and that split the queue exactly where keeping it in one file was meant to prevent — headings together, reasoning apart. Each line also carries **any other work item this one names that already has a session record — and whether that record is of the work being built, or only of its being processed in a planning run** — plus **the date the item first appeared in your queue**. All of these are facts you can check, never a judgment about what to do with them. The two kinds are told apart by reading the record rather than by its name, because a planning run writes a record for each item it *processes* and a build writes one for each item it *builds*, so the name alone cannot separate them. Getting that wrong is not cosmetic: the same signal decides what may be lifted out of the held region, so reading agreed-but-unbuilt work as finished would release work that depends on it. Records in older formats carry neither marker and are reported as found but unclassified rather than guessed at — partial coverage, said plainly. An item leaning on work already finished has a premise worth re-reading before it is built; an item leaning on work that was only agreed has a weaker premise still. A separate block lists **every file named by two or more items**, which is where work that can be settled together shows up. It also counts, for any work marked `Runs alone`, **how many ready items sit ahead of it** — because such work is reached only once everything before it is built, and every planning run adds newly ready work ahead of it, so a correctly placed item quietly recedes each time the queue is worked. A count is reportable where an age is not: how long something has been ready would need a threshold nobody can derive, while what sits in front of it is arithmetic. The digest also reports **placement contradictions**: an item sitting in the ready region whose own text says it must not be built or was returned unbuilt, an item whose file list names nothing to change, and a loop of work waiting on itself — which can never be released, unlike an ordinary chain of waiting work, which resolves the moment its far end does and is already visible on each item's own line. It also flags **work resting on a superseded finding**: research you've filed under `workshop/resources/research/` gets a `Superseded by:` line at the top when it's overtaken, and any work item naming that file is flagged so the correction reaches the decisions built on it — otherwise a citation runs one way, and a finding that turns out to be wrong leaves every piece of work scoped against it silently wrong too. That flag reaches only items that *name* the file; work resting on a finding it never cites isn't caught, and the digest says so rather than letting you read it as complete coverage. **A finding another project owns is copied in rather than pointed at**, carrying a line naming the owning project — never a path to it, because a path that identifies a person or an organisation must not sit in a committed document. Work resting on such a copy is then flagged as resting on a **snapshot**. That is a permanent label and not a staleness check: nothing reads the other project's folder, so nothing can tell you whether the original has changed since, and the flag says only that what you are building on is a copy taken on a date. These are surfaced for you and never acted on — moving work out of the ready region is your decision. The point is that work is otherwise checked on the way in and never looked at again, so an item can rot in place after it was placed correctly. **The digest also answers a narrower question on demand: what is next.** Which item comes next has to be worked out again every time one is picked, because the queue changes underneath the answer — items leave it, get set aside, new ones land — and re-printing the whole digest to establish that costs far more than the answer is worth. So it can instead return just the next pick: which rung of the ordering ladder the run fell to, that rung's top item, and where in the file that item starts. This is also what makes the claim further down — that every rung of the ladder reads a computed field — true rather than aspirational, since the count of how many other entries cite an item's slug is computed here and nowhere else. **The method also carries rules for maintaining your own SPEC**, applied whenever a session edits it — from either site, planning or a build that discovers it needs a SPEC change. Three of them: what belongs in SPEC at all (product truth, not how a thing is implemented), that the reasoning behind a decision goes to the session record rather than into the SPEC sentence, and that a SPEC sentence describing something the project no longer does is a defect to correct rather than clutter to tolerate. **There is no size limit and no growth report**, because SPEC has a floor a rule list doesn't: it has to describe your product as it actually is, so a true sentence about a live feature can never be removed to save room.
- `/next` — pick the top piece of ready work and execute it, routed by its flavor: a **build** (Claude edits files) or an **`[audit]`** — a first-class review pass where Claude reads and reports findings for later review, without editing. (Audit is its own flavor with its own discipline; it never edits on the spot.) A `[user]` item is a walk-through rather than something Claude runs — reserved for work Claude genuinely can't do or witness (a check that needs your eyes, a decision only you can make, a physical action), never for work Claude could run itself but is only blocked from running yet. Claude leads by walking you through it live, one step at a time — running whatever parts it can and guiding the rest through the concrete steps the item carries — and names how to close it out only once you've finished: run /done, or mention it at the next /plan. A **`[freeform]`** item is one /next must not run at all — work you and Claude do by hand in a session of its own, because it is large or because it characteristically can't run inside a /next run. Repairs to the machinery /next itself depends on are one such case, where using a broken mechanism to fix itself is the risk, but they are an example rather than the definition. /next halts on one rather than skipping past it, and a close that finds one waiting says so. /next works the cleared queue top-down — building each ready item and committing at the close — so a single invocation can clear several vetted items in a row without confirming each one, finishing at the readiness line, and it never proposes doing fewer items than the line allows: the line is the run's bound and it is set during planning. A run has one other bound, and only one: an item marked **`Runs alone`** is work that is ready to build but must not share a run with other work, because a run in flight holds the file paths it is working from — a rename, a folder move, or a migration that moves paths underneath a run makes those stale mid-build. /next stops before it rather than sweeping it into a longer run, saying plainly why, and builds it on its own next time. The bound keys on the run performing the work: an item the run finds already done — its observable check satisfied before any step is driven — closes, and the run continues, since no paths moved and there is nothing to protect. The marker binds /next and nothing else; it never claims the work can't be done alongside other work by hand.
- `/rescan` — look back over the conversation for anything decided, noticed or asked for that was never written into a file, and file it. **What it finds is routed by the standard triage rather than always becoming a capture:** work still to do goes to the queue, and what already *happened* — including work done after a close — is appended to this session's record as a marked tail. That is what makes it the one-word route for a post-close tail, which is common and otherwise has to be asked for in prose every time. **It still commits nothing**: the tail rides the next close's commit, so this is not a second close under another name, and because it can be run as many times as the tail has parts, nothing ever has to judge when the tail has ended. **User-invoked, never positional** — though where the method itself names the close as the next step, it recommends running /rescan first, so anything decided but never written down is caught before the session ends. Repeatable within one chat: it scans back only as far as the last /rescan, so running it twice does not re-surface the same things. It **files and never routes or builds** — the standing filing-vs-processing boundary, and the reason it does not build is that the installed plugin is a frozen copy, so a fix made mid-chat could not reach the chat that made it anyway. **Running it costs you nothing you were in the middle of: where something else was under way, it hands back and that work carries on.** That is what makes "run it whenever" true rather than merely offered — and it is why what a scan turns up can be settled by the session that found it, which is usually the one that still has the material in mind, instead of waiting for a later planning run. Nothing was ever technically lost by running it: a skill's instructions stay in the conversation for the rest of the session, so nothing is exited and nothing has to be restarted. What went wrong was that the wording said otherwise, and the wording is what a session follows. Its stopping point is held in the conversation with no durable marker; where that memory is gone, the captures already filed are the boundary. **And where the conversation cannot account for work the files record — the build's own working file lists thirty items ticked and the conversation shows six — it says so loudly, because that is two counts disagreeing rather than a judgement about memory.** The asymmetry is the safety property and is never softened: missing artifacts are positive evidence that earlier material has dropped out of view, while *present* artifacts prove only that the recent stretch is intact and say nothing at all about the earliest — which is precisely what the scan reaches for, since summarising takes the oldest material first. So the check raises a warning and never gives an all-clear; a session reporting "I can see everything, so nothing was lost" would hand the user a false guarantee at the one moment they are relying on the scan to be complete. The close keeps a shrunken version of the same step, looking back only to wherever /rescan last stopped — so a chat that invokes it pays a line at the close, and a chat that never does gets the full scan it always got.
- `/done` — close the build, record what happened, commit. Run on its own after changing files by hand (no /next first), it records and commits those edits too — reading them as the user's expected work, not a broken repo, and splitting them across separate log entries by judgment when they cover several distinct changes. It also records a completed `[user]` item once you've done it — logging it and removing it from the queue — so a finished step doesn't sit there and get brought back to you next time; /plan does the same when you mention a `[user]` step you finished between sessions. **The close tells you what the next work is and stops there — it never invites you into another build in the same conversation, and never ends by putting a command in front of you.** A conversation carrying a finished build and its close is the opposite of the fresh start the method is designed around, and a message that ends by asking a question whose answer looks like a command is one keystroke from being sent by accident, which happened. It also distinguishes work that is ready to build from work that still needs planning, rather than pointing at a build run that would immediately stop. **And where work continues after the close and changes a file, it offers once to append that to the session's record** — added as a marked tail rather than blended in, so what was recorded at the close stays visible, and only where something actually changed. A close may also amend an existing work item on the user's direction, recording the amendment in the session record under that item's name; where Claude rather than the user notices a problem with a cleared item, it stays a filing — the close names the collision plainly, and the item runs before the next planning session unless the user directs the amendment then and there. **A session makes exactly one commit — the close.** Anything that lands after it rides into the next session's close, so the working tree is expected to hold uncommitted changes between one close and the next; the "uncommitted changes from a previous session" line at a session's opening reports that normal state, not a problem.

Three project docs structure each project:
- `SPEC.md` — product truth. What the app is, who it's for, how it works. **It is read at build time, not only at planning time:** /next reads it once at the start of a run, so each item is built against it and can be checked against it. A build never rewrites SPEC to match what it did — it reports a contradiction and lets the user decide which is wrong. **A build never writes product truth at all, and the reason is a session boundary rather than a scope rule:** the session that made a choice is not the session that certifies it in SPEC, because one instance of Claude describing its own work in product truth is justification rather than specification. So planning writes the sentence, ahead of the build — the decision step asks whether a piece of work changes what SPEC says, and the sentence is written there, with the user present. SPEC therefore leads the build rather than trailing it, which is what reading it at build time requires. Where planning misses one, the build records the sentence it thinks SPEC owes and **files it as work rather than writing it**, so the next planning run writes it; SPEC lags that one sentence until then, visibly, as a queue item rather than in silence. The one gate that syncs SPEC to a decision runs at the /plan close, where the decision is made.
- `QUEUE.md` — processed and unprocessed work. Processed work is vetted and ready to build; unprocessed work is captured ideas and tasks not yet fully processed — either not yet discussed, or discussed and worth doing but not yet designed enough to describe the build. One item per piece of work. **A build reads this file: at the start of a run it reads the queue's cleared region whole, each item's full text with its reasoning inline.** The reasoning travels under a stated purpose: it is read to aim the work — it explains why the thing is worth building and is not itself part of what is built. A boundary rule states what unwarranted inclusion looks like: reasoning lands in a file the build writes only where that file is the record of the decision — the session's own LOG entry — or where the item specifically instructs it; in every other file the build writes the action the reasoning justifies, and not the reasoning. A kept item's instructions are written for a reader with less context and possibly less capability than the session writing them — which files change, what changes inside them, the observation that shows the change landed **together with any files that observation reaches**, any option already refused, one line each, and **the external facts the design rests on, with when each was last verified** — so the build infers neither the work nor the why, and a premise going stale is visible on the item instead of silent. The observation's files are named because they are routinely different ones — the test suite that has to pass, the sibling document an acceptance check greps — and a build that first meets them when its safety check refuses them has to stop and ask, which is the one thing a run nobody is watching should not need to do. The cost is stated rather than hidden: a run reads the whole cleared region to build it, and the guard against reasoning reaching shipped documents is the stated purpose and boundary rather than structural withholding.
- `LOG/` — per-session records of what was built, tested, and decided. Its index is split by month — the current month's lines in the main index file, older months in their own — and a lookup searches the index files rather than reading them whole, so the archive can grow without any single read growing with it; a planning session's opening still reads, unprompted, the index lines newer than the most recent planning session's record — the work done since anyone last stood at that opening.

**`workshop/` — where a project's working material lives.** Every project gets one, and it holds what the project works with rather than what it ships: research findings and re-read-later testing evidence under `workshop/resources/`, alongside whatever else a project keeps but does not publish — post drafts, article drafts, reference material it refers to. The split is what someone landing on the repository sees first: the product and the method's own documents stay at the root, where they demonstrate the method, and everything the project merely refers to sits in one folder that can be skipped. The distinction is tracked-versus-ignored as well as placement — machinery a close depends on is moved rather than ignored, because an ignored file lives on one machine with no history to restore it from, while content that genuinely isn't the project's is ignored outright. `resources/` was previously a root folder holding the same two kinds; moving it inside `workshop/` is a format change, so an existing project halts at its next session until /setup migrates it.

**Subprojects — popping an outgrown subpart into its own project.** When /setup runs in a folder that sits inside an already-adopted project, it offers pop-out framing: it reads the parent's product truth, guesses which subpart this folder covers, asks the user to confirm, and states plainly that there is no scripted way back in — pop-out is for subparts that have genuinely outgrown the parent, such as one unmanageable piece of a large differentiated project. The new project is an ordinary project in every respect and never reads outward. Dependencies run upward only, one level deep: subproject work can hold parent work, never the reverse — a cross-project loop is structurally impossible that way, and a child genuinely waiting on its parent uses the ordinary outside-the-project pattern instead (name what would show it done, or wait for the user to mention it). No session ever writes another project's queue: a dependency crossing the boundary travels as approval-gated mail, and the receiving project files it with its own hands. The parent keeps no list of its children — subprojects are subfolders, re-detected from the filesystem each session — and a parent item held on subproject work is checked at the parent's planning opening by reading that child's log index, the one circumscribed cross-project read.

**Cross-project INBOX — projects that can message each other.** Claude Code itself can message sessions that are open right now; the INBOX's delta is different — durable, offline, approval-gated mail, which reaches a project whether or not anything is running there and never sends without the user seeing the words. A user running several projects on the method gets an `INBOX/` folder in each, scaffolded at /setup. One project writes a message file straight into another's INBOX; `session_start` **names each waiting message and directs the session to read it, with a self-check on the reading** — the same shape it already uses for the behaviour rules, which is a far larger file and is trusted because the check is there. The bodies are deliberately not inlined, and the constraint is a real one rather than a preference: Claude Code caps a hook's output at 10,000 characters, and past that the harness discards the whole payload and substitutes a short preview, so enough unread mail would cost a session its project state, its queue facts and its rules directive as well as its mail. Inlining was tried first, because an instruction to go and open a file is a step and a step can be skipped — which happened, in a session that then reproduced twice the bug the unread message described. A directive carrying a check is what answers that without paying the ceiling. **A message is data, not an instruction to the session that receives it** — it is another project's report, and only the user's own words direct the work. An arriving message is still routed through the standard triage — work to do becomes a capture, a finding goes to the LOG, evidence to re-read goes under `workshop/resources/` — and the file then moves to `INBOX/archive/` so it isn't raised again. **Mail is routed at the opening of both /plan and /next**, before either does anything with the queue — the reading is already done by delivery, so what those openings guarantee is the triage and the archiving. At /plan that means anything a message contains is ordinary queued work by the time work is ranked. At /next it happens before the run is presented, so a message that bears on something about to be built can still change what runs: /next opens the mail, files whatever it raises as a capture, and can recommend dropping an affected item from that run alone — it never decides an item's fate, which stays planning work. A reply, where one is owed, is drafted at the close rather than mid-run, because a run is unattended in practice and nothing leaves the machine without you seeing the exact wording. **The close triages whatever is still waiting** — reading, routing and archiving it — which is what catches mail that arrived mid-session, since the close is the one skill that always runs. Otherwise the mailbox is scanned at the next session start. A project only ever reads its own INBOX; it never scans other projects for mail. **What sending guarantees is stated plainly rather than left to be assumed: it places a file in the recipient's mailbox, and nothing confirms it was read.** Before writing, the sender checks the recipient actually has a mailbox and says so when it has to create one — a project set up before mailboxes existed has nothing at its session start that surfaces waiting mail, so a message can sit there indefinitely with neither side knowing. An automatic read-receipt is rejected rather than merely unbuilt, because a receipt is an automatic send and nothing leaves the machine unapproved. **What the project sends is recorded too, in one index inside the mailbox — `INBOX/sent.md`** — one line per outbound artifact, whether it is mail, a problem report, a GitHub issue, a public post or a draft handed to another project: the date, where it went, whether it was handed over **for completion or only for continuation**, what it claimed, and a pointer to the text that already exists. The line is written in the same turn as the approved send, because the exact wording exists at that moment and nothing later reconstructs it. It exists because a mailbox holding only received messages records half a correspondence, and because two questions were otherwise unanswerable: what did we send that project, and did we ever announce the behaviour this change has just replaced. The intent is what lets a send close work: handing an item to another project **for completion** can clear it, while handing it over for continuation leaves it in the queue. It sits inside `INBOX/` because that folder is never committed and these lines name other projects — the same reason the address book lives there, and with the same cost, that it is not version-controlled and can be lost. **A correspondent's folder path is recorded on first use, inside `INBOX/`**, so continuing a conversation doesn't make the user retrieve the path again — it is a record of what they supplied or directed Claude to find, and it lives inside the mailbox folder because the gitignore covers that folder and everything beneath it, keeping paths that identify a person out of any published repository. Supplying includes pointing rather than typing: on the user's ask, Claude runs a bounded search for the folder they name and confirms the match with them before recording or sending. What never happens is an unprompted scan for other projects. **That record is write-and-send only**: Claude may pass a recorded path to a send, and may never quote it, name a correspondent in any document, or carry either into chat — because the gitignore protects against publication and nothing else, and the real exposure is a session copying a name out of the address book into a file that does get committed. **Before writing into a recipient's mailbox, the sender also confirms that project's `INBOX/` is actually covered by its own `.gitignore`, and refuses to send until the user says go where it is not** — a message written into a repository whose ignore rules this project does not control would otherwise be committed there. **Nothing is ever sent without the user approving the exact wording**, because a message carries one project's content into another and both mailboxes may sit in repositories that get published — the same human backstop, for the same reason, as the feedback report. **`INBOX/` is gitignored on every path — at /setup and at migration — and no question is asked. That protects against publication and nothing else**: the files still sit in plain text on disk, readable by any session in the project, which is why what may be done with their contents is restricted separately. A read message is archived rather than deleted, so a mailbox left in the repository accumulates another project's raw text forever, after its useful content has already been carried into the queue in this project's own words. The safe outcome must not depend on a question, because a question is skippable — and the migration path skipped it. Where a project already has INBOX files in its git history, /setup says so plainly rather than implying the ignore line undoes it.

Three hooks enforce discipline mechanically, and a fourth advises:
- `session_start` — detect project state, load behaviour rules, surface the queue's dependency facts in one line (how much work is ready, how much is held, and how many of the things it waits on are themselves unprocessed — emitted even when all three are zero, so a computed zero can't be mistaken for a check that never ran; it also **names** which held item waits on which blocker, and which held items name a blocker that is in neither section, which is the signal that something may be ready to lift), report today's date read from the clock (the anchor every date decision reads instead of deriving "today" by assumption; stated as the date at session start, since a long chat can cross midnight), report the installed snapshot's install date alongside its version and content stamp (a readable fact from the plugin cache, so a session weighing how long a build has been in place reads a date rather than guessing — the fact bare, never a verdict on how tested the build is), report **whether this session is isolated from any other session open on the project** (measured, never assumed — it decides which parallel-session advice applies). There are **three** isolation cases, not two: an ordinary shared working tree, a linked worktree, and a **clone inside a cloud container** — which is what a session started from the mobile or web app runs on. A clone is a main checkout, so the git comparison alone would call it a shared tree and give it the one piece of advice that actively misleads, that collisions are handled; the cloud case is therefore detected from the environment first, and told plainly that its work reaches the main machine only as a pushed branch. It also reports **any worktree carrying commits this checkout doesn't have**, so an isolated session's work can be offered a merge rather than stranded on a branch nobody is tracking (the offer happens in a main-checkout session, since git refuses to update a branch checked out elsewhere). **Those worktrees are classified rather than merely listed**: one inside the project's own `.claude/worktrees/` is where Claude Code allocates a session's worktree, so it is session work and the merge is offered; one anywhere else is a deliberate long-lived worktree and is never offered. The classification fails in one direction only — if the worktree location has been changed from its default, real session work is called deliberate and goes unoffered, which is a missed offer rather than a wrong one, name any **working file left behind by a session that never closed** (surfaced, never deleted, since it can hold the only record of what that session did), report — where the project has a cycles doc — each cycle definition, its cadence and what its observable currently reads (facts, never a verdict on whether a turn is due, which the skills compute), and halt the session when the project's documents are on an older format than the installed plugin expects (see Keeping projects current). The facts are inputs, not instructions: /plan turns them into its throughput recommendation, and other skills ignore them.
- `pre_tool_use` — enforces the scope-lock (which governs SPEC.md like any other file) and git safety. The lock reaches planning sessions too, against a **standing** list rather than a build's agreed one: a planning session may write your queue, your spec, your session records, your FAQ, your cycles doc, your research notes and its own scratch files, and a write to anything else is refused rather than offered to you for approval. The refusal is the point — an approval request that gets waved through is not consent, and a planning session is where a change should become a piece of queued work instead of an edit. What it costs is stated rather than discovered: a genuinely needed change outside that list now stops the session and becomes an item, where it used to be one sentence. The one carve-out is a `[freeform]` item's own session: it opens by declaring the file list its queued item carries, written where the hook reads it, and the lock then enforces that agreed list — so hand-work runs under the same discipline as a build instead of being denied the files its own item names. and asks for your approval before Claude spawns a subagent (a cost guard that asks, never blocks). It also blocks any attempt to write one of your files through a script rather than through the editing tools — whatever the file is, and whether or not it's in the current work's scope — pointing Claude at the editing tools instead, or at the purpose-built queue tool for large queue edits. A script whose target file is *worked out as it runs* rather than written down is blocked too, since a target nobody can read cannot be shown to be safe; the accepted cost is that a genuinely harmless scratch write has to name its file plainly. It also refuses to overwrite an existing session record — a new record written under a name that is already taken would destroy the old one silently, so the hook names the next free filename instead. Appending to an existing record is untouched. **The outbound register is guarded the same way**: `INBOX/sent.md` — the one-line index of everything the project has sent or posted — sits inside a mailbox that is gitignored on every path, so unlike every other project document it has no history to restore from and an accidental deletion is final. A whole-file write over it, or a shell command that deletes or truncates it, is refused; appending and editing pass through untouched. The register is not un-ignored to fix this, because the folder's ignore is what keeps the address book's identifying paths out of a published repository, and a project's outbound record is not necessarily something its owner wants public. The limit is stated rather than implied: a hook sees only what goes through Claude's tools, so a file deleted outside the app, or a lost disk, is not reached by this.
- `stop` — checks Claude's finished response for a report that names a capture as filed, and confirms that entry is actually in your queue — or already on record as built work: a slug with a session record in `LOG/`, or one ticked in this run's own working file, is finished work being cited, not a failed filing. If it isn't, the turn is fed back so the write can be made and you can be told plainly what happened, before you act on a report of work that doesn't exist. It catches reports that *name* the item; a vague "I've written that up" escapes it, which is accepted rather than hidden, since the rule already requires a report to name what landed. It blocks once per claim and then stops blocking, so a genuine mismatch can't trap the conversation.
- `post_tool_use` — advisory QUEUE.md structure lint; flags format drift, never blocks. It runs after an edit lands on the queue **and after any shell command**, since a write reaching the queue through a script bypasses the editing tools entirely. It also scans QUEUE.md, SPEC.md and LOG entries for things shaped like credentials — private keys, API tokens, email addresses.

**Privacy posture, settled at setup.** Scaffolding offers once to keep `SPEC.md`, `QUEUE.md` and `LOG/` out of the repository via `.gitignore`, so they are never tracked or published — and the offer is **per document rather than all three together**, because the combination someone most plausibly wants is a private queue with a public history, and a bundled choice makes that unreachable rather than merely un-defaulted. It stays one question with three answers rather than becoming three questions. No default changes: nothing is ignored unless the user asks for it. The trade is stated when it's offered, and it is larger than "you lose undo". **Three behaviours change for whichever documents are untracked, and the method says so rather than letting them fail quietly.** Claude normally writes to a project doc first and reports what landed, on the test that the previous version is recoverable without the user's help — for an untracked file it is not, so those writes are shown before they happen instead. A deleted queue item is genuinely gone rather than kept by history. And the close can no longer read back its own work from the file's diff, so it records from what it remembers of the session. **The method also detects this at every session opening rather than trusting the choice to be remembered**, because the state can arrive from an ignore file the user wrote themselves, or from a choice made weeks earlier in a project nobody has looked at since — and it was found, in a real project, only when a whole planning session's record turned out never to have been tracked. What it reports is which documents are untracked and what follows; it never calls the configuration wrong, since this is a choice the method itself offers. It is part of scaffolding rather than a sixth interview question, because it is answerable without knowing anything about the project. Declining keep-private is followed by a plain statement of what results — documents tracked in this folder's history and readable nowhere else until the project has an online home, set up whenever the user asks — and the visibility answer is written as a standing line in the project's own CLAUDE.md, where every later session reads it, rather than only in the setup session's record. A session that brings a second git repository inside the project — a clone, a fork, a fresh init in a subfolder — says so at that moment, names which repository holds the method's documents, and puts the root choice to the user, recording the answer the same way; setup runs the same check when it adopts a folder with existing content. **A public repository is set up only when the user asks for one**, never volunteered, and the licence question travels with that offer rather than sitting in the interview — a licence only becomes a real question once the code is going somewhere public, and asked earlier it is one most non-coders cannot answer while still describing what their app is. The cost is named: someone who never asks for a public repository never considers licensing at all. **The offer may set up the repository and may never represent the contents as screened** — that would contradict the limit below, and the honest thing to say is that not publishing these documents is the only complete protection. The idea that open source implies open logging is deliberately not surfaced at setup: raising it at all nudges toward publishing planning documents, which is the direction that limit exists to avoid nudging.

**What the scrub gate does and does not promise.** The scan above catches credential *shapes* only: deterministic, no judgement, so it never produces false confidence. Alongside it, Claude reads what it is about to write against a checklist — personal names, case details, third-party data, identifying paths — at the three moments text enters a committed doc: filing a capture, keeping one as a work item, writing a LOG entry. A person other than the project's own user is referred to by the identity they have published on GitHub — username, pronouns where supplied, first name only where they put it there; anything they have not published is rewritten away like any other personal detail.

The limit is stated deliberately and must never be softened. The checklist is Claude checking its own writing, and no pattern can tell whether a sentence quietly identifies a real person — which is the thing that actually leaks from these files. So the method never tells a user their artifacts are scrubbed or safe to publish. A gate that over-claims is worse than no gate, because the user publishes more freely believing it worked. This is the same line the method holds on red flags: provide risk-*addressing*, never promise risk *management*. For a repository that will be public, the only real protection is not publishing these artifacts at all.

**Editing-state signal — a published contract other apps can read.** While Claude is writing a file, the hooks publish a small marker saying so, so another application open on the same document — a Markdown reader or editor the user is reading and typing in — can hold off rather than the two landing on top of each other. It replaces a guess with a fact: a watcher can see *that* a file changed but not *who* changed it, and a wrong guess locks the user out of their own document mid-sentence.

It is a **heartbeat, not a lock**, and that is what makes it safe: every marker carries a fresh timestamp, a reader treats a stale one as "not editing" whatever its flag says, and a missing marker means nothing is happening. So it fails open — a crashed session can never lock the user out of their own document, and the overwhelming majority of projects, which never have this plugin installed, are unaffected.

**The field-level contract lives in [EDITING-STATE-CONTRACT.md](EDITING-STATE-CONTRACT.md)**, at the repository root. It is a published interface another application is built against, so it needs a home a consumer can find and cite — which is not this document. What belongs here is what the product does; what the JSON fields are called belongs there.

One rules doc steers everything the hooks can't enforce:
- `skill-nonspecific-rules.md` — loaded at every session start in adopted projects. It opens with a short statement of what the method is for — intent surviving whatever Claude remembers, approving as the product rather than overhead — so every session, including one running no skill, carries the point and not only the procedure; each skill doc's opening line ties that skill's job to the same purpose. It carries only rules that fire whatever is running, which is what its name states and what admits a rule to it: communication, capture routing, dependency ownership, file safety, and five response-shape tags ([SILENT], [BRIEF], [DISCUSS], [PROMPT], [SEQUENCE]) that procedure docs place on individual steps to control verbosity and interaction. A rule that fires inside one skill lives in that skill's own doc instead, where it is paid only when that skill runs. Rules are stated bare, with the reasoning kept out of the operative statement; where a reason is genuinely needed to apply a rule correctly, it is reclassified as operative text and written into the rule itself rather than kept as an attached why-clause. Material whose trigger is unmissable is fetched on demand rather than always-loaded (the consumer feedback channel and the INBOX mechanics live in `feedback-and-inbox.md`), so the always-loaded set stays within the number of instructions a model follows reliably.

**The plugin ships a brevity output style, offered at /setup and enabled per project with the user's consent.** It keeps Claude Code's built-in coding instructions and carries the method's brevity and communication-shape steering at system-prompt level. The offer is opt-out with acceptance as the default: /setup first checks whether the user already has an output style set, names it and any contradictions with ours, explains why acceptance is strongly preferable — verbose models produce runaway verbosity in doc-heavy projects and weigh sessions down with unnecessary narrative — states that the setting applies to this project only, and invites discussion before setup continues. On acceptance the setting is written into the project's own settings file; the style never applies itself, and the user's own style file is never edited. Existing projects receive the same offer through the top-up. Every session opening checks the setting: where the style is not enabled, one short line says so; where it is, nothing. Styles reach the main conversation only and take effect at the next session or /clear. The always-loaded docs stay canonical and complete, so a project that declines the style is fully governed; the style deliberately restates the method's communication rules at system-prompt level, which is its mechanism rather than a duplication to shed. A rule living only in the style is a defect — it is a promotion candidate for the always-loaded rules, since a declining project would otherwise never receive it.

**Write-first approval.** Claude writes to the project's docs first and reports what landed, rather than pasting a draft into chat and waiting for approval before writing. Which moments work that way is settled by one test rather than a memorised list — **is the previous version recoverable without the user's help?** Queue items and captures, LOG entries, SPEC edits and ordinary build edits all answer yes: they are tracked in git, so an unwanted change costs a revert and nothing else; consent happens in conversation, in plain words, before the write, and the file is the record of what was agreed rather than where agreement happens. One further case is shown before writing: a close-time or /rescan candidate set — several ideas landing at once at the session's end — is shown as one numbered message the user contests by number. Three kinds answer no and are still shown before they happen: a **commit message**, because a commit is materially harder to unwind and the message never becomes file content, so "write it first" has no meaning for it; anything that **leaves the machine** — the feedback report, an outbound INBOX message — where no revert reaches the copy already delivered; and a **wholesale conversion of a document the user already owns** where git does not yet hold it, which is what /setup's queue migration does to a project that may have been adopted moments ago. That third case is the test applied, not an exception bolted on: the wording used to ask whether a revert would undo it, which quietly assumed a safety net that a freshly adopted project may not have.

**And the user can ask for show-first at any time**, for the rest of that session — the switch moves only toward more showing, so the three cases above stay show-first regardless. It is held in the session and never stored, because it records where the user is right now rather than anything stable about them. Separately, a session can be asked to paste doc-bound text inline instead of linking to it; in a /next run that also displays each edit's new wording inline, with Claude naming any items large enough that inline display would bury the run. Showing an edit is visibility, not approval — the work was agreed at planning time — so it never makes a run wait. A single test rather than an enumerated carve-out survives new approval moments being added later, which a list would silently omit. The report after a write is one line naming what landed and where, pointing at the artifact, never a re-paste of the text just written — approval has already happened in conversation before the write, so the report is a receipt naming the record rather than a request to read it. What keeps the reading affordable is the artifact's own word band. The trade is stated rather than discovered: show-first guaranteed unapproved text never reached disk, and write-first means a file briefly holds content the user has not agreed to — cheap and recoverable in a git repository, but rejection becomes a revert rather than a non-event, and the risk it introduces is not rejection but the user not noticing, which is why the report has to name its artifact precisely enough that the user knows which one to open.

**View-in-doc rendering.** Text that already lives in a project doc (an existing queue item, a just-written capture or log entry, a readable edit) is surfaced as a one-line pointer plus a link to the file, rather than re-pasted into chat — the token-saving default, and unconditional: there is no stored setting gating it. Text that isn't written yet has nothing to point at, so it appears inline. Links are plain file links and never promise a line anchor: the desktop app opens `.md` in its own viewer and ignores the anchor, so where a line matters it is named in the surrounding prose instead. Pointing is the unprompted default, and nothing detects a reason to depart from it. **The one departure is spoken: where the user says they can't open the file — they're on a phone, driving the session remotely, reading over someone's shoulder — doc-resident text comes into the message instead, for the rest of that conversation.** Nothing is stored and nothing is inferred, because a rule that asked Claude to work out where the reader is would make it interrogate them, which is the cost this design exists to avoid; the switch moves one way only, toward more showing. The general offer to paste doc-bound text inline for a session is retired, because every item's discussion now opens with a plain-English summary inline — the reader away from the file is served by the summary for one item, and the spoken trigger is what covers a long set they're being asked to approve piece by piece. Two settings that used to govern this, a stored working mode and a recorded editor, are retired: the app opens `.md` whatever editor is named, and the location field recorded how much text the user wanted pasted rather than where they were. A stale field in an existing project is ignored silently.

**Co-authored drafts are handed over as an editable file, not as chat text.** Where a walkthrough step has the user editing something Claude drafted, the draft is written to a `.txt` file and the step names where it is — `.txt` being the format the desktop side panel opens for editing, with a save button, so the user decides when their edits land. Claude then reads the file back only when the user says to, asks whether there is anything else, and repeats until the user says they are finished. The user edits the text directly instead of describing the change they want, which is what stops co-authored work collapsing into Claude work the user writes into.

**No completion asks on `[user]` work.** A `[user]` step is walked through and nothing more: no session — building, planning or closing — ever asks whether one is already done, leading, trailing or in passing. Completion is *inferred* from what a session can see: a step walked to its end this session is done, a step whose prerequisite visibly hasn't cleared isn't, and the user mentioning one is the third way. A walk-through also opens by reading any session records under the item's name, so a step the record shows performed is not re-run — a partly done multi-step item resumes where the record leaves off. Where a step leaves an observable result — a URL responding, a branch gone, a file present — the method checks the world rather than accepting the report, because a step was once logged complete when the work had in fact been blocked. The gap this leaves is deliberate and documented: a step completed privately, with nothing observable to show for it, sits in the queue until the user mentions it. One narrow exception, keyed on two recorded facts together: where an item's own record shows it was handed to the user for completion after a close, and it names no observable the method can reach, the session that would otherwise re-drive it asks once where the work landed instead of re-presenting it — an item without a recorded hand-over never qualifies. And every `[user]` item a run touched ends on one of three recorded outcomes — **done, deferred, or not reached** — with "deferred" written only from the user's own word, never inferred; "not reached" tells a later session to present the item fresh, so the record never claims a decision the user did not make. The `Completion mode:` setting that once toggled a planning-time sweep is retired; a stale field in an existing project is ignored silently.

**Readiness line.** /plan maintains a line in the queue — rendered `--- Cleared to run above this line ---` — that marks which work is vetted and safe to build (above it) from work that still needs planning (below it). It is positioned at the close of a /plan run — the single close (run by /done) that always fires however the session ends, so the positioning is never silently skipped — and Claude narrates where it sits whenever the line moves, confirming silently when its placement is unchanged, so the user never has to work out by hand how much of the queue is safe to run next without being told the same boundary twice. /next inherits it as its run bound when it works several items in a row — a clean finish at the line rather than running into unvetted work.

**Lifting shelved work.** Work sits below the readiness line for exactly two reasons, and each is written on the item itself: **other named work in the queue blocks it** (`Blocked by:`, naming one or more items), or **a date it must not be built before has not yet passed** (`Not before: YYYY-MM-DD`). Where the field names several items the work lifts only when every one of them resolves, which is how work that waits on a whole group gets held at all — naming a single stand-in would set it loose the moment that one item shipped, with the rest outstanding, and because lifting is a clearing move the work would then reach the ready region and be built out of order. The queue lint checks both fields — that every slug resolves to a real entry in the queue, and that a date is a real one. Work waiting on anything else *outside* the queue — a restart, a site going live, someone else's reply — is not shelved with a note about the wait; the awaited thing is filed as its own queue item, so it gets planned and done like any other work, and the held item names it. A date is the exception because it needs nobody: every other blocker takes a human or a build to resolve, while a date is read off the calendar by the hooks, so a queue item standing in for one costs a planning run to answer a question nobody has to think about. **A date is also the one hold that reaches unprocessed captures, where it means something different — not "don't build this yet" but "don't offer this again before this date."** It is written there only with the user's approval, for a capture waiting on something outside the project entirely: another project's reply, or a feature shipping in a tool nobody here controls. Such a capture can name no blocker, because nothing in the queue can do what it is waiting for, and it can never be held below the readiness line either, since being held there requires work specific enough to build. Without this it returns to the top of the queue every session and is set aside again. It remains a capture throughout and gains no state of its own: the queue still has two sections and one readiness line, and this is one existing field appearing in one more place. At the start of every /plan, Claude checks one thing per shelved item — has its blocker shipped, or has its date passed? — and proposes lifting the ones that are ready. Nothing is asked of the user, because the answer is in the record and the calendar rather than in their memory.

This replaced a model where the wait was recorded as a prose sentence inside the held item and re-interpreted each session. That failed in a specific way: a blocker written as a sentence inside another item is invisible as work, so nobody picks it up. One item sat shelved for weeks on a step buried in its wait-sentence, and became visible the moment it was filed as its own line. **Work whose completion happens outside the project is handled by checking rather than by being told.** Nothing notifies this project that work handed to another one is finished — a mailbox delivery is never guaranteed to be read, so a notice would move that problem rather than close it. Instead, work waiting on something outside the project **names what would show it done** — a page to load, a file to look for, a branch that should be gone — and that is checked when the work is reached; where nothing observable exists, the work says so, and waits until the user mentions it. Saying so is the part that matters, because it is what tells a later run to ask instead of guessing which case it is in. Relatedly, before any work is tagged `[user]` at all, the method names the tool that would do it and confirms that tool is absent or unavailable — a check rather than a judgment, because work that merely *sounds* manual has been handed to the user when a command-line tool could do it in seconds.

**Tool facts — a home for what a project has on hand.** Facts about a project's environment that are expensive to re-derive — a tool installed and working at a known path, a build command that fails specifically from Claude's shell — live in a `TOOLS.md` at the project root, created the first time a session has such a fact to record; a project with none has no file and pays nothing. Any session may write a fact there the moment it is learned, and a build's environment check reads it before assuming a tool or environment is absent — so an assumption that once cost a run its first act becomes a lookup.

**Cycles — recurring maintenance on request.** A user can put an artifact on a cycle: a named piece of recurring work — a weekly release, a posting rhythm, a maintenance pass — defined once and then driven by the queue like everything else. Definitions live in a dedicated cycles doc the project gains the first time one is asked for, and a project with no cycles has no doc and pays nothing. A definition names the artifact, the steps of one turn, the cadence (declared or derived — either way it says which), and **the observable that marks a completed turn** — a release's date, a sent-record line — because position is never stored: at the openings and closes of /plan and /next the method reads the definitions, computes each cycle's due-ness from its observable, and files one capture per due step, satisfied while an open capture with its slug exists. Wherever a cycles doc exists the check says in one line which cycles are due and which are not, whether or not anything is filed, so a check that ran and found nothing due is distinguishable from one that never ran. Due cycle work therefore enters the queue and is weighed like any other work, rather than standing on a board nobody is obliged to read; several artifacts can ride the same cadence separately, each computing its own position. A capture a cycle claims as its material — marked with a `Cycle:` line naming the definition — is drawn by that cycle's turns rather than ranked by the planning order, and returns to ordinary ranking by itself if the cycle is ever deleted. A cycle's rhythm is deliberately independent of the work cycle's own — running /next often does not make a weekly release come sooner. And cycles are suggested, not only asked for: where planning meets recurring-shaped work — the same artifact worked repeatedly — Claude offers a cycle once, in the message already discussing that work, and creating one stays the user's call. A cycle's steps can also stand alone as a **ritual** — a named, reusable step list with no schedule, defined in the same cycles doc and run when the user asks for it by name. Rituals are suggested the same way: where planning meets procedure-shaped work — the same multi-step sequence done on request more than once — Claude offers once to write it down as a ritual, and a ritual that gains a cadence and an observable becomes a cycle. Creating or promoting either stays the user's call. **A ritual definition also names the paths its steps write.** A planning session may only write a short standing list of the project's documents, and a ritual's steps often need somewhere outside it — a build folder, a generated artifact — so the definition says where, and the safety check reads the project's own cycles doc instead of carrying a hard-coded exception for each one. Those paths are permitted whenever the project is open rather than only while the ritual runs, because nothing marks a ritual as running and the single exception that already worked this way has never needed one. The trade is stated rather than hidden: a path a definition names is writable in any session, so it is worth naming narrowly.

**Ports — running the method somewhere other than Claude Code.** Throughliner is a Claude Code plugin, so it does not simply run elsewhere; what it consists of is plain documents plus small scripts that fire at particular moments in a session, and a port is somebody mapping those moments onto another tool's. That mapping is judgement and stays with the porter. **Two flavours are recognised, named, and both are supported** — **tracking**, which follows this project closely, takes its changes as they come, and carries as many of its features as the other tool allows; and **independent**, which is its own thing — its own name, its own decisions, adopting only the changes it wants. The names exist because a flavour nobody can name is a promise nobody can read. Naming them is what makes a port legible, because otherwise nobody, including this project, can tell what a given port is promising. **What the original owes a port that wants to keep up is a changelog written for ports**, produced per release: what changed inside which shipped file and why, derived from the boundary that already exists — everything inside the plugin package ships and everything outside it is the development project's own, so a port following the session records blind would otherwise carry across work never meant to leave. It marks a format change that would migrate a port's own users' documents, and it states its limits: it says what changed and never how to map it, and a change to a hook may have no equivalent on the other side at all.

**Self-hosting seed — for users building their own method or port.** A user who is developing a method, plugin or port of their own — authoring rules their own sessions will follow — can say so at /setup, or ask later on an already-adopted project, and the scaffolding seeds the self-authoring discipline as an add-only augmentation: a self-hosting block in the project's CLAUDE.md carrying the rule gate (admission, eviction, distribution, wording), the disposition-recorded-on-the-item pattern with its session-record line, and the host-versus-target framing, plus template files for a retired-terms register and a compliance-audit checklist. It never overwrites anything the user wrote, and it deliberately excludes the development project's own release rituals and tooling, which do not generalise.

**Seeding the queue from SPEC.** A rich SPEC — especially one a deep /setup interview produced — describes buildable features that may have no path into the queue, so the whole feature set can "die in SPEC" with nothing to build it. /plan can seed the backlog from SPEC to close that gap: it offers this automatically only in the narrow thin-queue/rich-SPEC state (Processed empty or near-empty while SPEC describes real unbuilt features), and the user can invoke it manually any time. The user chooses the granularity — a few coarse milestones or granular per-feature items — and the derived items land in Unprocessed as ordinary captures for later processing, never straight into Processed. Seeding lives in /plan, not /setup: /setup stays scaffolding and interview, and never spawns work on its own.

**Processing flow.** A /plan run opens on two beats, in this order. First the triage: a skim for items obviously not worth doing, offered as one numbered batch to drop — the user contests by number, and the pass can only drop, never advance work. It fires only when something is obviously droppable, and it comes first because there is no point ordering items about to be deleted. Then one question: anything the user wants to prioritise, or shall Claude order them the usual way? "The usual way" signals that a standard order is being applied without naming which rule it falls to — because the order used is often the fallback ladder rather than any nameable default. The one-line narration that follows names, in plain words, the order Claude picked — the question itself names no order, because the order used is often the fallback rather than any nameable default. Where an uncleared red flag tops the order, the question is asymmetric instead: the flag is stated as what comes first unless the user names something definitely more important. That single question replaces what used to be a separate "anything to discuss?" opening, so the run asks two things where it once asked three. The reorder that follows applies whatever the user chose, and recommends a floor for how many items to process this run. Where nothing meaningfully unblocks anything else, the order falls through an internal ladder of four rungs — an uncleared red flag in the unprocessed queue first, then unblock-potential (how many other entries cite this one's slug, most-cited first), then the entries that are **both** longer and older than the section's middle, oldest first, and beneath those a single alternating rung: **oldest first, with every other pick required to be one of the long entries.** The long half is everything at or above the section's median line count; the third rung is where that half overlaps the older half by filing date. Both sets are fixed when the run opens. **Every rung either reads a field the queue digest already computes or subtracts two line numbers**, so ordering costs no judgment. Line count is deliberately the arithmetic and not an impression of length: an entry's last line minus its first, with nothing counting words and nothing reading the entry to place it. **Length decides membership and never order.** Working the long entries first is what shortens the queue fastest, since long entries are what make it expensive to reason across — but line count is not a stable key, because an entry grows while it is being processed, so ranking by it means the entry ranked last can overtake the one ranked first with nobody touching the ladder. The date an entry was filed cannot change. **The long half is therefore fixed when the run opens and never recomputed**: an entry that swelled past the median mid-session would re-enter a group already worked past, the group would stop shrinking, and a rung that ranks without ever yielding makes everything beneath it unreachable by construction — which is what the earlier ladder did. The median is a proportion of the section it orders, computed and printed by the digest at each opening, so no figure is written into the method's text. **The third rung is an intersection, and it is bounded because of it.** An entry both long and old is one that has been enriched across many sessions without resolving, so this rung reaches the work that keeps coming back rather than the best-designed work — an earlier ladder rested on the second claim and the evidence did not support it. Two overlapping halves make roughly a quarter of the section, a set small enough to finish inside one run, which is what lets it sit above the alternation without starving it; the earlier rung took half the section and was never once emptied. **It depends on captures being able to bow out**: an entry that cannot yet be built would otherwise be handed to the user first every session, which is why a capture may carry a date that stops it being re-offered. **Alternating is what makes decay reachable at all.** Age-ordering alone within the long half would still never reach a short old entry, and ordering the two concerns one after the other — by size then date, or date then size — only relabels the problem, since one key dominates and the other starves under a new name. Alternation needs no weighting, and a weight would be a bare number nobody can derive. The case it serves is a long queue whose owner does not get through the full set for many sessions: for that person entries genuinely rot, and every earlier ladder left them unreached in practice while claiming to reach them in principle. It reads the **date filed** rather than file order, because the queue can be reordered on request and a file-order rung would then rank by something that had just been overwritten. **Staleness in the other sense is still not an ordering concern**: an item whose premise names work that has already shipped is flagged in the digest at the session opening, where the user sees it, rather than pulling the item forward — a different fact from how long the entry has been waiting. The ladder is applied and narrated, never offered as a choice: the user sees one line naming the order used. The turn that opens discussion of an item begins with a plain-English summary of what the item says, inline and before any analysis — the pointer to the file stays for whoever reads it, and the summary serves the user who doesn't — and the recommendation that follows states in plain words what would actually change and asks agreement in those words, never as a bare procedure term. During the one-at-a-time pass, each item's checkpoint lets the user skip an item for a later session — skipping sets it aside for the rest of that session and does not move it in the file, so the queue keeps recording the order things landed. **An item skipped because it will not design out names what would settle it and who owns that** — a decision the user owns, a fact to look up, or a build that must ship first — **and where the answer is a decision the user owns, Claude asks before skipping rather than deferring again.** Planning is the one moment they are there, and an item that is enriched every session without the one available question ever being put is an item nobody is deciding — and a capture the user raises mid-session comes with an offer to process it now or carry on, given before the idea is analysed or designed, so the user is never made to feel their idea was parked or the choice pre-spent. A `[user]` item filed during planning may be walked through immediately, with the user present, where doing it now clears a red flag or unblocks the session's own work — the item is written into the queue before its first step, so an interrupted walk survives. **And a planning run never offers to stop while unprocessed work remains** — the same promise the close already makes about not inviting another build. Naming a few items to start with sets the order, not the length of the run, so when those are done the next item is simply presented. The question that offers to wrap up is available only once nothing is left but items set aside for later; used any earlier it quietly recasts a full queue as nothing left to do, which happened with thirty-five items still waiting. It is asked once, when the queue first comes to rest; if work resumes and the queue comes to rest again in the same stretch, the session ends plainly with no second ask, and the question fires again only after further work has filled and emptied the queue once more. New captures are added to the end of the queue rather than slotted in beside related work; a relationship between two items is written into the items themselves, where it survives any reordering.

**Close-out pass: batching the stops that need you.** At the close of a /plan run — the same always-run /done close that positions the readiness line — Claude makes one pass over the ready section, moving `[user]` steps and `[audit]` reviews to the end so the moments needing your attention sit together instead of interrupting a run partway through. Claude does it and says so; it isn't a question.

**That is the only reordering the close does, and the reduction is deliberate.** It used to re-derive the order of both sections. Neither re-derivation earned its cost. Everything above the readiness line is built by a single run, so its internal order rarely changes anything — and where two pieces of work genuinely affect each other, that is written into the work itself, which survives being moved where sitting next to each other does not. The unprocessed section is ordered at the start of the next planning run anyway, at the moment the order is actually used, so computing a lasting order at the close meant computing something its only reader immediately recomputed. Left alone, the queue reads in the order things landed, which tells you more than a ranking that was already stale.

**Forward-recommendation advisory.** When /done closes a session with a concrete recommendation for what to plan or build next, it files a "Last session advises…" note at the top of Unprocessed — advice, not a command. The next /plan reads it and deletes it in the same breath — surfacing it is what consumes it, unless the note carries a condition to persist longer. The clear sits at the read because the session reading the note is the one that can tell it is spent: it used to happen at that session's close, which meant a build run passing between two planning runs left a consumed note behind, and the next /plan opened on advice about work that had already shipped. Clearing at the read means the note is gone even if the planning session then ends without acting on it, which is accepted — the advisory is orientation rather than work, and a session that read it has had the orientation it was for. A close that files its own advisory and finds a spent one in the slot replaces it — deleting the spent note and saying it did — so the read-clears-it rule covers only notes a close is not replacing. The note never moves into Processed and is never treated as real work; it's a transient handoff so the recommendation survives across sessions without depending on anyone's memory. The close also records whether it filed that note or judged one unnecessary, as an explicit line in the session record, and cannot complete until it has — a step that produces no artifact when skipped is indistinguishable from one that ran and found nothing to file, which is how it came to fire about half the time.

**Multi-item /next.** /next is the single queue-clearing runner. Invoked when the user wants ready work built, it works the cleared region of the queue top-down, building each item scope-locked; a single invocation can build several cleared items back-to-back without confirming each one. The close commits the run — one item's LOG entry verbatim when only one built, a summary commit when several did, each item still keeping its own LOG entry. It finishes cleanly at the readiness line, or earlier at an item marked `Runs alone`. **Work raised mid-run that isn't part of what's being built is captured rather than done, and the run says why in one clause** — the run stays on agreed work, and the new thing gets weighed against everything still to come rather than being decided by whoever is in the room. **Asking a second time for the same thing carries a small change (a file or two) straight through**, since a repeated request is the user's decision; a large or half-designed one still gets a proposal to split, because a repeated request doesn't make a big change small.

**A direct request is warned about once, then done.** Where the user directly asks for something now and a rule of the method would hold it back, they get one standalone warning turn — what the request crosses, the risk, and briefly what could be done instead — and the work proceeds on their next word, whatever that word is; both the warning and the work are recorded. The warning is its own turn so the request can still be withdrawn, and asking a second time is not what unlocks the work. Two gates stand unchanged: nothing leaves the machine without an explicit yes to the exact text, and destruction git cannot undo still goes through the file-safety rules. This is a promise about who decides — the user does, informed — not a loophole in either gate.

**A run is not left alone, and the method says so rather than calling it unattended.** What is true, and what every "don't interrupt this" rule rests on, is that it does not confirm each item and moves faster than a person can follow — so stopping it to ask costs far more than the question is worth. What is not true is that it runs to completion by itself. It pauses to walk a `[user]` item through live, it halts outright on `[freeform]` work, and it never closes itself, because the close is the user's command to run — so a run left alone finishes its builds and sits there uncommitted until someone returns. A user who reads "unattended" and walks away is the person this misleads. It works because /plan feeds it a well-vetted cleared region: a no-progress stop (halting if the same error, empty diff, or failing check repeats on one item) keeps a stuck item from thrashing unwatched, and a red flag rides its work item into the build with its cleared state recorded in the LOG.

**Keeping projects current.** The plugin keeps improving while projects sit set up, so a project can fall behind what the current method scaffolds. At the start of a working session, before /plan or /next, `session_start` catches this three ways: it flags whole docs or folders the project is missing (offering /setup to add them), it tops up an existing doc that's missing a newer *setting* the method has since added, and — the strongest of the three — it **halts the session outright** when the project's documents are on an older *format* than the plugin expects. **A plugin version change on its own produces no notice and calls for nothing.** Only the three checks above ask for /setup, and each says so when it fires; the installed version is reported at every session opening regardless. **While /setup is outstanding, /next also checks whether the run it is about to present contains work /setup would overtake** — an item naming a file /setup rewrites from a template that may already carry the correct text — and recommends dropping just that item from that run, never deciding its fate. It fires only on that collision rather than on every run in a behind project, because a warning that appears whether or not it applies is one people learn to read past. The case is real: a project elsewhere ran a whole build and close whose top item was void before it started. /setup backs that up at the point of running: it **refuses outright while a build is in progress**, since it would otherwise fail file by file against the build's safety check rather than stopping cleanly at the door, and in a planning session it **describes what is about to happen and lets the user choose** — no refusal there, because nothing is blocked, but silence is the failure to avoid.

The halt exists because the other two only notice what's absent, and the damaging case is a file that is present but on a shape the method no longer reads correctly: nothing errors, so /plan and /next spend the whole session reasoning over stale scaffolding and report a confidently wrong picture. Each project records its format in a `.throughliner-format-epoch` marker and the plugin declares the current one; when the project is behind, the session opens by saying so and pointing at /setup, which migrates the documents rather than replacing them. The format number is deliberately **not** the plugin version — the version changes at every release, most of which change no format, so a version check would cry wolf and be learned-past. Detecting the format by inspecting the documents' structure was rejected for the same reason in reverse: it guesses, about files users legitimately hand-edit. The user can override the halt and carry on; they're told once that results may be unreliable until the migration runs. The top-up is add-only — it never rewrites or clobbers anything the user has written; where a setting needs an answer (like which editor they work in), Claude opens with a one-line question and writes the answer, and settings needing no answer are added silently with a note. The missing-setting check is a list, so new settings join it over time. **A fourth thing is reported rather than checked for: an artifact a retired feature left behind.** When the method retires something that generated a file, that file stays put in every project that already had one — nothing produces it, nothing reads it, and working out what it is takes reading the plugin's source. So the plugin ships a list of retired artifacts, and a session opening names any of them still sitting in the project, with what produced it. It reports and never deletes; removing a file from someone's project is exactly what the add-only posture exists to prevent, and whether to keep it is theirs to decide. The riskier case — reconciling content whose template wording changed — stays deliberately out of scope for the user's own text: overwriting a paragraph the user may have written themselves is the thing that must not happen. The one exception is the plugin-managed block of a project's CLAUDE.md, which is method-owned: migration refreshes that region, reports what it replaced, and moves any user-authored lines found inside it below the end marker rather than overwriting them. What is in scope is the strictly smaller half, **detecting retired terms**: the migration reads the project's own CLAUDE.md for names of method pieces that no longer exist — a queue of batches with Build/Test/Audit sub-headings, a Deferred tests section, `Parked:` headers — and reports each one alongside what replaced it. It reports and edits nothing, so it can never clobber their words, and the decision about their own file stays theirs. The gap it closes is real and was reported from a live project: that description was written at setup and is read at the start of every session since, so a session goes looking for a section the method removed months ago and has to work out from scratch that it is gone.

**Reporting a problem — three destinations, one question.** A user's problem is with one of three things, and each has its own home. Their **app** is ordinary work and stays as a capture in their QUEUE. The **method** — a skill misbehaving, a confusing step, a rule with a bad outcome — has nowhere useful to go in their own project, so it routes out to the plugin's author at flintcraft.tech/report. **Claude Code itself** — the app the method runs inside, its viewer, its links, its hooks machinery — belongs to Anthropic, and routes to a GitHub issue on `anthropics/claude-code`. Claude decides by asking which thing is misbehaving, and asks the user rather than guessing when it genuinely can't tell. Where the plugin's own development project is recorded as a correspondent in the project's mailbox address book, a method problem routes to it as approval-gated mail instead — the public routes remain for everyone else.

Both outward routes are scrubbed by construction — what happened, which step, the version; never the user's app details or secrets — and neither sends anything the user hasn't seen and approved. They differ only in mechanics, deliberately: a method report is offered as a GitHub issue on the plugin's own repository where the `gh` CLI exists — posted on an explicit yes, with the offer stating plainly that an issue is public under the reporter's own account — and the web form where the CLI is absent or the reporter prefers privacy; a Claude Code report can be filed with `gh`, so Claude posts it on an explicit yes rather than sending a non-coder to a GitHub form, falling back to a draft-and-paste when `gh` isn't available. Where the sender wants a reply, the send files one dated follow-up capture naming the agreed way to check — the issue's comments, or for a form report an email route where a suitable email connection exists and the user approves it — and it surfaces in a planning session once the date passes; no reply wanted, nothing filed. Answers on filed issues, and new issues arriving on a project's own repository, are surfaced by the planning opening's correspondence scan where the CLI and a repository exist. **A third limb reaches issues the account is involved in on repositories the project does not own** — the ones that bear on the work and belong to nobody here, like a bug in the tool the method runs inside. It is narrowed by activity rather than by relevance: only issues that have moved since the last planning record are surfaced, which turns a standing list into the few worth reading, and whether one of those actually bears on the project stays a judgement made with the user rather than a filter pretending to be mechanical. Issue text is written by strangers, so it is treated as data and summarised in the project's own words, never followed as instruction. **The bound is stated rather than implied: it reaches issues the account is involved in, so one nobody here has touched stays invisible.** The Claude Code route also searches existing issues first — which shapes the report rather than merely avoiding duplicates, since knowing the adjacent issues is what lets a report distinguish itself. Either the user or Claude can raise a report; when Claude notices something misbehaving it offers once, without nagging.

## Principles

- Never restrict ideation, just direct it. The user must be able to ideate at any point in the build cycle.
- Hooks enforce what must never happen; hardened rules and tags steer what should usually happen. Mechanical enforcement is cheap and unskippable; behavioural steering is written to survive priority conflicts on the models users actually run.
- Execution sessions trend toward pure execution. Ideas and discoveries can be captured anywhere, but deciding their fate is planning work and happens in planning sessions. This end state is realized as multi-item /next — a build mode that works the cleared queue without confirming each item, and pauses at three points: a `[user]` step it walks through, `[freeform]` work it must not run, and the close, which is the user's to invoke. It is not a mode that finishes on its own, and describing it as one sets an expectation the run does not meet.
- Surface risk in plain language; never bury it. Claude screens for data-exposure and breach risks and flags them where the user can't miss them. It doesn't silently ship past a security concern, and it doesn't let a risk be accepted without a recorded, informed choice.
- Readable output is a control requirement, not a style preference. The user keeps Claude aligned by reading and approving what it does, so output too long to get through breaks that control — an error the user can't read past is one they can't catch. "Be thorough" means surfacing every important thing the user must see and act on, never emitting every word: lead with the decision, then stop; gate detail behind an explicit request. This is anti-overwhelm, not terseness — the levers are sequencing and leading with the decision, never a word-count cap, and plain English for the non-coder is the standard the concision serves, not a cost it trades away.
