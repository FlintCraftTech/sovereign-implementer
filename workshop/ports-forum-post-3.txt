**3. Pulling changes into your own port**

A tracking port has to answer one question every release: what actually changed
in the shipped package, and which of it is none of my business? Reading the
session records will not tell you — most of what this project does never
leaves it.

**The changelog is written for that question.** Each release publishes a
port-facing changelog: what changed inside which shipped file, and why. It is
attached to the GitHub release and committed at the repository root as
`PORT-CHANGELOG.md`, so a clone has it without hunting a release page.

**The line it draws is the package boundary.** Everything under
`plugin/throughliner/` ships; everything outside it — the release rituals, the
rule-checking scripts, this project's own queue and records — is the
development project's own. **Host-only changes are marked as such, and must not
be ported.** That mark is the single most useful thing in the file: a porter
following the commit history blind carries across work that was never meant to
leave.

**Picking up after a gap.** If you last ported from an older version, don't
diff release by release:

```
py plugin/throughliner/scripts/port_changelog.py . --catch-up 1.19.0
```

That spans every release since, up to the current tip. It takes a tag, a
commit, or a bare version number.

**Three limits it states about itself**, and they are honest rather than
modest:

- it says **what** changed, never how to map it — the translating stays yours;
- a change to a hook **may have no equivalent** on your side at all;
- a **format-epoch bump** means your own users' documents need migrating, and
  that is yours to handle.

**Where it stands today:** one changelog is on `main` now, covering
v1.21.0..v1.21.1 — clone or pull and it is there. None has been attached to a
GitHub release yet, because no release has run since the generator shipped;
that starts with the next one.
